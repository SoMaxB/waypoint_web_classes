Clase 4 · NASM, ELF64 y herramientasClass 4 · NASM, ELF64 and tools

nasm · elf64 · object · ar · readelf · nm · gdb
Objetivo

Entender el viaje completo de un archivo .s hasta convertirse en un ejecutable o en libasm.a, y conocer las herramientas que permiten inspeccionar cada etapa (nasm, ld, ar, readelf, objdump, nm, gdb). Al terminar, debes poder explicar qué diferencia hay entre un objeto y un ejecutable, qué significan las columnas de una tabla de símbolos, por qué una biblioteca va al final del enlace y qué hace un breakpoint de GDB.

1. El viaje del código

archivo.s ──nasm──▶ archivo.o ──ld──▶ programa (o libasm.a)
                    "objeto"    "enlazador"

Un .o no es el mismo archivo que el ejecutable con otro nombre: es la misma información incompleta. El objeto contiene el código máquina pero con instrucciones a medio rellenar; el enlazador completa esos huecos.

Los tres verbos son distintos:

nasm  = ENSAMBLAR   (texto .s  → bytes .o, con huecos)
ld    = ENLAZAR     (resolver huecos uniendo objetos)
gcc   = COMPILAR    (C → ensamblador; llega en la clase 5)

2. El objeto .o: secciones, símbolos y relocaciones

Secciones

Un objeto se divide en secciones. En NASM se declaran con section:

section .text     ; código: se ejecuta, no se escribe
section .data     ; variables que cambian en tiempo de ejecución
section .rodata   ; constantes de solo lectura (cadenas, tablas)
section .bss      ; variables sin valor inicial (se reservan, no se guardan)

Dentro del objeto, todas las secciones aparecen en dirección 0x0000...0000: todavía no tienen dirección final. Se la asigna el enlazador.

Tabla de símbolos

Un objeto tiene una tabla de símbolos. Las columnas que importan:

UND    = "necesito esto, viene de fuera"   → lo resuelve el enlazador
GLOBAL = "estoy definido y visible"        → otros objetos pueden usarme
LOCAL  = "existo pero no salgo"            → útil para etiquetas internas

En NASM, global ft_x declara un símbolo visible y extern ft_y declara que el símbolo viene de otro objeto.

Relocaciones

Cuando un objeto referencia un símbolo externo, el ensamblador deja un hueco con un marcador. La sección de relocaciones es la lista de "huecos por rellenar". Por ejemplo, para call ft_destino, la relocación dice:

en el desplazamiento 1 de .text hay 4 bytes que deben rellenarse
con la dirección de ft_destino

El enlazador es quien rellena esos huecos con la dirección real.

3. El enlazador ld

ld une objetos y bibliotecas, asigna direcciones a las secciones y resuelve todas las referencias UND.

Demostración real: si salta.o llama a ft_destino definido en dest.o, después de enlazar:

Antes  (en salta.o):      ft_destino aparece como UND y hay una relocación
Después (en el ejecutable): ft_destino aparece DEFINIDO (p. ej. 0x401010)
                           y no quedan relocaciones

El desensamblado con objdump -d -M intel confirma que el hueco se rellenó:

call 401010 <ft_destino>

Matiz importante: el símbolo no "se define al ensamblar". ft_destino ya estaba definido en su archivo; lo que ocurre en el enlace es que la referencia se resuelve.

4. Secciones y permisos en el ejecutable

En el ejecutable, cada sección ocupa su propia zona de memoria con permisos distintos:

Sección   Dirección    Permisos
.text     0x401000     R E   (se lee y se ejecuta)
.rodata   0x402000     R     (solo se lee)
.data     0x403008     R W   (se lee y se escribe)

Ninguna sección se pierde ni se mezcla en un único bloque: el SO marca .text como no escribible y .data como no ejecutable. Es una medida de seguridad. Separarlas también significa que escribir sobre .rodata o sobre .text produce un fallo de segmentación. Por eso las cadenas que se modifican (destino de ft_strcpy, resultado de ft_strdup) viven en memoria de escritura, mientras que las literales van a .rodata.

5. La biblioteca estática

Un archivo .a es un contenedor de objetos .o, un "zip sin comprimir". Su firma de archivo lo delata: empieza con los bytes !<arch>.

ar  r  c  s  libx.a  a.o  b.o
    │  │  │   └──────────┐───────────┘
    │  │  │              └─ objetos que se meten en la caja
    │  │  └─ "s": generar índice de símbolos
    │  └─ "c": crear si no existe
    └─ "r": reemplazar/añadir objetos

El índice (s) permite al enlazador saber en qué miembro está cada símbolo sin leer toda la caja. Cuando un programa enlaza contra libx.a, el enlazador solo extrae los objetos que resuelven símbolos pendientes, no todos.

6. El orden del enlace

La regla más importante: la biblioteca va al final del comando, después de los objetos que la usan.

ld main.o libx.a        → OK
ld libx.a main.o        → FALLA
ld main.o libx.a ft_c.o  → FALLA
ld main.o libx.a libx.a  → OK (repetir la lib nunca rompe)

El enlazador procesa los argumentos de izquierda a derecha. Al llegar a una biblioteca, extrae solo los miembros que resuelven símbolos ya pendientes en ese momento; si la pasa sin pendientes, no extrae nada y no vuelve atrás. Por eso:

libx.a main.o       → cuando se ve la lib, nadie ha pedido ft_c todavía: extrae NADA
main.o libx.a c.o   → cuando se ve la lib, solo ft_c_es pendiente (y libx.a no lo
                    tiene); las referencias que llegan después, tarde

Consecuencia para el Makefile de la clase 10: el orden será $(CC) tests.o libasm.a.

El peligro del comodín *.o

ar rcs libasm.a *.o funciona, pero arrastra todo lo que haya en la carpeta, incluidos objetos de prueba con su _start. Una biblioteca de entrega debe contener exactamente sus objetos:

ar rcs libasm.a ft_strlen.o ft_strcpy.o ft_strcmp.o ft_write.o ft_read.o ft_strdup.o

Con nm libasm.a | grep " T " se verifica que la biblioteca exporta exactamente los seis símbolos obligatorios y nada más.

7. GDB: congelar el tiempo

GDB no sirve para "ejecutar", sino para detener la ejecución en un punto y comparar el estado real con el esperado.

  • Un breakpoint (punto de parada) detiene la CPU antes de ejecutar la instrucción marcada: los registros muestran el estado previo.
  • info registers rax rdi muestra el valor de esos registros en el instante congelado.
  • rip indica la dirección de la instrucción congelada.
  • x/5bx $rdi+$rax lee memoria en bruto (bytes hexadecimales), que es como el ensamblador ve el mundo. En el formato x/5bx: x = examine memoria, 5 = cantidad, b = unidades de 1 byte, x = mostrar en hexadecimal.

La primera pregunta ante cualquier bug en ensamblador no es "¿dónde está el error del algoritmo?" sino:

¿En qué estado está la CPU ahora? ¿Coincide con el estado que yo esperaba?

En C, un bug suele ser una línea mala; en ensamblador casi siempre es un desajuste de estado: un registro con un valor inesperado, un puntero que avanzó de más, un flag distinto al esperado.

Objective

Understand the full journey of a .s file until it becomes an executable or libasm.a, and learn the tools that inspect each stage (nasm, ld, ar, readelf, objdump, nm, gdb). By the end you must be able to explain the difference between an object and an executable, what a symbol table's columns mean, why a library goes at the end of the link, and what a GDB breakpoint does.

1. The journey of the code

file.s ──nasm──▶ file.o ──ld──▶ program (or lib.a)
        "object"    "linker"

A .o is not the same file as the executable under another name: it is the same but incomplete information. The object contains the machine code with placeholders still to fill; the linker fills those gaps.

The three verbs are different:

nasm  = ASSEMBLE  (text .s → bytes .o, with gaps)
ld    = LINK      (resolve gaps by joining objects)
gcc   = COMPILE   (C → assembly; comes in class 5)

2. The object .o: sections, symbols and relocations

Sections

An object is split into sections. In NASM they are declared with section:

section .text     ; code: executed, not written
section .data     ; variables that change at runtime
section .rodata   ; read-only constants (strings, tables)
section .bss      ; uninitialized variables (reserved, not stored)

Inside the object, all sections appear at address 0x0000...0000: they do not have a final address yet. The linker assigns it.

Symbol table

An object has a symbol table. The columns that matter:

UND    = "I need this, it comes from outside"   → the linker resolves it
GLOBAL = "I am defined and visible"             → other objects can use me
LOCAL  = "I exist but I do not leave"           → useful for internal labels

In NASM, global ft_x declares a visible symbol and extern ft_y declares that the symbol comes from another object.

Relocations

When an object references an external symbol, the assembler leaves a gap with a marker. The relocation section is the list of "gaps to fill". For example, for call ft_destino, the relocation says:

at offset 1 of .text there are 4 bytes that must be filled
with the address of ft_destino

The linker is the one who fills those gaps with the real address.

3. The linker ld

ld joins objects and libraries, assigns addresses to sections and resolves every UND reference.

Real demonstration: if salta.o calls ft_destino defined in dest.o, after linking:

Before (in salta.o):       ft_destino appears as UND and there is a relocation
After (in the executable): ft_destino appears DEFINED (e.g. 0x401010)
                           and no relocations remain

Disassembling with objdump -d -M intel confirms the gap was filled:

call 401010 <ft_destino>

Key nuance: the symbol is not "defined at assembly". ft_destino was already defined in its file; what happens during linking is that the reference gets resolved.

4. Sections and permissions in the executable

In the executable, each section occupies its own memory area with different permissions:

Section   Address    Permissions
.text     0x400000   R E   (readable and executable)
.rodata   0x402000   R     (read-only)
.data     0x403008   R W   (readable and writable)

No section is lost or merged into a single block: the OS marks .text as non-writable and .data as non-executable. It is a security measure. Separating them also means that writing over .rodata or .text causes a segmentation fault. That is why strings that get modified (destination of ft_strcpy, result of ft_strdup) live in writable memory, while literals go to .rodata.

5. The static library

A .a file is a container of .o objects, an "uncompressed zip". Its file signature gives it away: it starts with the bytes !<arch>.

ar  r  c  s  libx.a  a.o  b.o
    │  │  │   └──────────┐───────────┘
    │  │  │              └─ objects put into the box
    │  │  └─ "s": generate the symbol index
    │  └─ "c": create if it does not exist
    └─ "r": replace/add objects

The index (s) lets the linker know where each symbol is without reading the whole box. When a program links against libx.a, the linker extracts only the objects that resolve pending symbols, not all.

6. Link order

The most important rule: the library goes at the end of the command, after the objects that use it.

ld main.o libx.a        → OK
ld libx.a main.o        → FAILS
ld main.o libx.a ft_c.o → FAILS
ld main.o libx.a libx.a → OK (repeating the lib never breaks)

The linker processes arguments left to right. When it reaches a library, it extracts only the members that resolve symbols already pending at that moment; if it passes it with nothing pending, it extracts nothing and never goes back. That is why:

libx.a main.o     → when the lib is seen, nobody has asked for ft_a yet: extracts NOTHING
main.o libx.a c.o → when the lib is seen, only ft_c is pending (and libx.a does not
                   have it); the reference to ft_a comes later, too late

Consequence for the class-10 Makefile: the order will be $(CC) tests.o libasm.a.

The danger of the *.o wildcard

ar rcs libasm.a *.o works, but it drags in everything in the folder, including test objects with their _start. A deliverable library must contain exactly its own objects:

ar rcs libasm.a ft_strlen.o ft_strcpy.o ft_strcmp.o ft_write.o ft_read.o ft_strdup.o

With nm libasm.a | grep " T " you verify the library exports exactly the six required symbols and nothing else.

7. GDB: freezing time

GDB is not for "running", but for stopping execution at a point and comparing reality with the expected state.

  • A breakpoint stops the CPU before executing the marked instruction: registers show the previous state.
  • info registers rax rdi shows the value of those registers at the frozen instant.
  • rip holds the address of the frozen instruction.
  • x/5bx $rdi+$rax reads raw memory (hexadecimal bytes), which is how an assembler sees the world. In the format x/5bx: x = examine memory, 5 = count, b = units of 1 byte, x = show in hexadecimal.

The first question for any assembly bug is not "where is the algorithm wrong?" but

What state is the CPU in now? Does it match the state I expected?

8. Tools of the class

nasm      text .s → object .o   (nasm -f elf64 file.s -o file.o)
ld        objects + libs → executable (resolves gaps and addresses)
ar        groups objects into .a libraries (ar rcs lib.a a.o b.o)
readelf   inspects headers, sections, symbols and relocations of an ELF
objdump   disassembles: shows machine code with Intel syntax
nm        lists the symbols of an object or library
gdb       debugger: breakpoints, registers, memory

  • Thinking the .o and the executable are the same file under another name; in the .o external references are not yet resolved.

  • Hunting the bug in the algorithm before checking the real register/memory state.
