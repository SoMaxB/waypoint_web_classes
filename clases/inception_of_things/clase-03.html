Clase 3 · Kubernetes básico y p2Class 3 · Basic Kubernetes and p2

ConfigMap · Deployment · Service · Ingress · Traefik
Objetivo

Entender cómo Kubernetes ejecuta tres aplicaciones en una sola VM y las expone con un único Ingress que enruta según la cabecera Host. Al terminar: explicar qué son un ConfigMap, un Deployment, un ReplicaSet y un Pod, cómo se pegan con labels y selectors, qué aporta la IP estable del Service ClusterIP, cómo decide Traefik por cabecera, y seguir curl -H "Host: app2.com" http://192.168.56.110 desde el host hasta uno de los Pods, demostrando el balanceo de las 3 réplicas.

1. La topología de p2 — ficheros

En srcs/p2/ hay cuatro piezas:

srcs/p2/
├── Vagrantfile          1 VM (<login>S, 192.168.56.110), sin worker ni token
├── scripts/setup.sh     instala K3s y aplica los manifiestos con esperas
└── confs/
    ├── app1.yaml        1 réplica
    ├── app2.yaml        3 réplicas
    ├── app3.yaml        1 réplica, catch-all
    └── ingress.yaml     enrutado por Host
Los roles de cada fichero
FicheroRol
srcs/p2/Vagrantfile1 VM, IP fija, sin worker ni token: cluster de un nodo.
srcs/p2/scripts/setup.shInstala K3s y aplica los manifiestos con esperas (rollout status).
srcs/p2/confs/app{1,2,3}.yamlCada app: ConfigMap + Deployment + Service (sección 2).
srcs/p2/confs/ingress.yamlEnrutado por Host: app1.com→app1, app2.com→app2, sin host→app3.

El Vagrantfile

Lo nuevo frente a p1 es el orden de los provisioners (se ejecutan en el orden declarado):

server.vm.provision "file",   source: "confs", destination: "/home/vagrant/confs"
server.vm.provision "shell",  path: "scripts/setup.sh", args: [SERVER_IP]

El provisioner file sube la carpeta por SCP (igual en ambos providers, al contrario que el synced folder). Los manifiestos ya están dentro cuando corre el script.

setup.sh

until kubectl get nodes --no-headers 2>/dev/null | grep -q .; do sleep 3; done
kubectl wait --for=condition=Ready node --all --timeout=180s
kubectl apply -R -f "${CONFS}"                 # -R = recursivo
for app in app1 app2 app3; do
  kubectl rollout status "deploy/${app}" --timeout=180s
done
until kubectl -n kube-system get deploy traefik; do sleep 3; done
kubectl -n kube-system rollout status deploy/traefik --timeout=180s

Las esperas importan: K3s devuelve el control antes de que el API server esté listo (--no-headers), y Traefik se instala como un Job de Helm en el primer arranque. Sin ellas el vagrant up "termina bien" pero el curl falla.

2. Anatomía de appN.yaml — 3 objetos por fichero

Cada appN.yaml son tres documentos YAML separados por ---, siempre el mismo patrón:

┌─ ConfigMap  appN-nginx   configuración de nginx (incluye la página web)
├─ Deployment appN         cuántos Pods y con qué imagen
└─ Service    appN         IP/nombre estable + balanceo entre Pods

2.1 ConfigMap — la configuración es la página

apiVersion: v1
kind: ConfigMap
metadata:
  name: app1-nginx
data:
  default.conf: |
    server {
        listen 80;
        location / { return 200 "<h1>Hello from app1</h1>...pod: $hostname</p>"; }
    }
  • El bloque server es la conf de nginx. Con return 200 no hace falta imagen propia ni volumen con HTML.
  • Cada clave del data = un fichero. Al montarse en /etc/nginx/conf.d, default.conf aparece como /etc/nginx/conf.d/default.conf, justo el directorio que nginx lee al arrancar.
  • $hostname es variable de nginx → hostname del contenedor → nombre del Pod (app2-6f9f6f7b57-abcde). Por eso la respuesta muestra qué Pod contestó.

2.2 Deployment → ReplicaSet → Pod

apiVersion: apps/v1
kind: Deployment
metadata: { name: app2, labels: { app: app2 } }
spec:
  replicas: 3                      # app2=3; app1 y app3=1
  selector:
    matchLabels: { app: app2 }     # qué Pods gestiona
  template:
    metadata:
      labels: { app: app2 }        # DEBE coincidir con el selector
    spec:
      containers:
        - name: app2
          image: nginx:1.27-alpine
          ports: [{ containerPort: 80 }]
          volumeMounts: [{ name: conf, mountPath: /etc/nginx/conf.d }]
      volumes:
        - name: conf
          configMap: { name: app2-nginx }

El Deployment no crea Pods directamente: crea un ReplicaSet, y este mantiene el número exacto de Pods vivos:

Deployment (replicas: 3)
  └─ ReplicaSet (mantiene 3)
       ├─ Pod app2-xxx
       ├─ Pod app2-yyy
       └─ Pod app2-zzz

2.3 Service — IP/name estable, balancea

apiVersion: v1
kind: Service
metadata: { name: app2 }
spec:
  selector: { app: app2 }      # labels de los Pods a los que sirve
  ports:
    - port: 80                 # puerto del Service
      targetPort: 80           # puerto del contenedor (nginx)

Sin type, es ClusterIP: IP interna al cluster, no accesible desde fuera directamente. El Service no enruta por Host — solo selecciona y balancea. El acceso exterior lo da el Ingress.

3. Labels y selectors — el pegamento

Tres sitios con la misma etiqueta app: app2:

Deployment.spec.selector.matchLabels.app        = app2   ← qué Pods gestiona
Deployment.spec.template.metadata.labels.app   = app2   ← etiqueta de los Pods creados
Service.spec.selector.app                       = app2   ← a qué Pods manda tráfico

Si el selector del Service no coincide con los labels reales de los Pods, el Service queda con la lista de Endpoints vacía → el objeto existe pero "no sirve a nadie".

4. Ingress y Traefik — el enrutado por Host

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata: { name: apps }
spec:
  ingressClassName: traefik
  rules:
    - host: app1.com      → service app1     # regla NOMBRADA
    - host: app2.com      → service app2
    - http:               → service app3     # regla SIN host = default backend (catch-all)
  • Quién enruta: Traefik, el Ingress controller que K3s instala de serie (expuesto en el puerto 80 del nodo vía servicelb).
  • La clave del subject: una regla sin host actúa de default backend. "Any other Host → app3".
  • Sin DNS: todos los curls van a 192.168.56.110; Traefik decide por la cabecera Host. El /etc/hosts del host solo sirve para probar desde el navegador.

5. El viaje completo de una petición (la práctica del plan)

curl -H "Host: app2.com" http://192.168.56.110
  │
  ├─ 1. El host abre TCP a 192.168.56.110:80 (IP fija, sin DNS)
  ├─ 2. Entra por el servicelb de K3s (klipper) → Traefik
  ├─ 3. Traefik lee Host: app2.com → regla del Ingress → Service app2:80
  ├─ 4. Service app2 (ClusterIP) → kube-proxy elige 1 de sus 3 Endpoints (IPVS)
  └─ 5. nginx del Pod responde "pod: app2-xxxx-yyyy" ($hostname)

El balanceo físico lo hace kube-proxy (tablas IPVS/iptables del nodo), no el Service. Repitiendo el curl se ve el round-robin:

for i in 1 2 3 4 5 6; do curl -s -H "Host: app2.com" http://192.168.56.110 | grep pod; done
# pod: app2-6f9f6f7b57-abcde   ← cambia de Pod en cada petición
# pod: app2-8c2f8d5a4b-qwert

6. Diagnóstico rápido

Síntoma en p2CausaPrimer comando

Regla mental

rule missing → 404 · backend falla → 502 · backend no existe → 503.

Predicciones y ejercicios

Ejercicio 3.1 — $hostname y la prueba del balanceo

¿Qué valor toma $hostname en la página servida por nginx, y por qué sirve para demostrar el balanceo de app2?

Mostrar solución

$hostname es una variable de nginx que resuelve al hostname del contenedor. En Kubernetes ese hostname es el nombre del Pod, que el ReplicaSet genera único: app2-6f9f6f7b57-abcde. Como las 3 réplicas tienen pods con nombres distintos, al repetir el curl cambia el nombre en la respuesta → esa es la prueba viva de que el Service reparte entre las 3.

for i in 1 2 3 4 5 6; do curl -s -H "Host: app2.com" http://192.168.56.110 | grep pod; done

Ejercicio 3.2 — Service con selector roto

Si el Service app2 tuviera selector: { app: app2-wrong } (etiqueta que ningún Pod tiene), ¿qué vería el usuario y con qué comando se comprueba?

Mostrar solución

El Service queda con la lista de Endpoints vacía → el objeto existe pero no sirve a nadie.

kubectl get endpoints app2      # ENDPOINTS vacío  ← la prueba definitiva
kubectl describe svc app2       # ver el selector
kubectl get pods -l app=app2    # ¿los Pods tienen esa label?

El usuario recibe 503 Service Unavailable (no 502): el 503 es "el servicio existe pero no tiene Pods"; el 502 sería "sí hay backend, pero falla".

Ejercicio 3.3 — El enrutado sin DNS y el 404

¿Dónde vive la distinción entre app1.com y "cualquier otra cosa" si la IP es siempre la misma? ¿Y por qué una regla sin catch-all daría 404?

Mostrar solución
  • La IP solo decide a qué máquina llega; la distinción vive en la cabecera HTTP Host que Traefik lee y compara con las reglas del Ingress. No hay DNS en el curl.
  • Si no hay regla para ese Host y no existe la regla sin host, Traefik responde 404: no hay ninguna regla que gestione ese nombre. El catch-all convierte "404 potencial" en app3.

Ejercicio 3.4 — Ver el balanceo

¿Qué dos comandos muestran que los 3 Pods de app2 existen y que el Service los conoce?

Mostrar solución 
kubectl get pods -o wide          # 3 Pods de app2 (names únicos)
kubectl get endpoints app2        # IPs tras el Service app2 (3 endpoints)

Los pods los mantiene el ReplicaSet; la lista de IPs la publica el Service en Endpoints; kube-proxy la programa en iptables/IPVS para el balanceo.

Ejercicio 3.5 — La pregunta girada de defensa

"app1.com funciona pero un Host inventado cae en app3. ¿Está mal el DNS? ¿Añadiría una regla?"

Mostrar solución

No es un fallo, es el diseño del subject: "any other Host → app3". No hay DNS en juego con curl (IP fija + cabecera). No se añade la regla — el catch-all (regla sin host) es justo lo que pide el requisito; añadirla rompería "todo lo no contemplado va a app3". Es una regla de default backend, no un bug.

Errores frecuentes
  • Confundir port (puerto del Service) con targetPort (puerto del contenedor).
  • Creer que el Service enruta por Host → no, enruta el Ingress; el Service solo selecciona y balancea.
  • Pensar que $hostname es una variable del shell → es de nginx, y vale el nombre del Pod.
  • Selector del Service que no coincide con los labels de la plantilla del Deployment → Service sin Endpoints → 503.
  • Creer que app3 es un DNS → es la regla de Ingress sin host.
  • Diagnosticar 404/502/503 sin mirar primero kubectl get endpoints y kubectl describe ingress.

2. Anatomy of appN.yaml — 3 objects per file

Each appN.yaml is three YAML documents separated by ---, always the same pattern:

┌─ ConfigMap  appN-nginx   nginx configuration (includes the web page)
├─ Deployment appN         how many Pods and with which image
└─ Service    appN         stable IP/name + load balancing across Pods

2.1 ConfigMap — the config is the page

apiVersion: v1
kind: ConfigMap
metadata:
  name: app1-nginx
data:
  default.conf: |
    server {
        listen 80;
        location / { return 200 "<h1>Hello from app1</h1>...pod: $hostname</p>"; }
    }
  • The server block is the nginx config. With return 200 there is no need for a custom image or an HTML volume.
  • Each key in data = one file. Mounted at /etc/nginx/conf.d, default.conf becomes /etc/nginx/conf.d/default.conf, exactly the directory nginx reads at startup.
  • $hostname is an nginx variable → container hostname → Pod name (app2-6f9f6f7b57-abcde). That is why the response shows which Pod answered.

2.2 Deployment → ReplicaSet → Pod

apiVersion: apps/v1
kind: Deployment
metadata: { name: app2, labels: { app: app2 } }
spec:
  replicas: 3                      # app2=3; app1 and app3=1
  selector:
    matchLabels: { app: app2 }     # which Pods it manages
  template:
    metadata:
      labels: { app: app2 }        # MUST match the selector
    spec:
      containers:
        - name: app2
          image: nginx:1.27-alpine
          ports: [{ containerPort: 80 }]
          volumeMounts: [{ name: conf, mountPath: /etc/nginx/conf.d }]
      volumes:
        - name: conf
          configMap: { name: app2-nginx }

The Deployment does not create Pods directly: it creates a ReplicaSet, and the ReplicaSet keeps the exact number of Pods alive:

Deployment (replicas: 3)
  └─ ReplicaSet (keeps 3)
       ├─ Pod app2-xxx
       ├─ Pod app2-yyy
       └─ Pod app2-zzz

2.3 Service — stable IP/name, load balances

apiVersion: v1
kind: Service
metadata: { name: app2 }
spec:
  selector: { app: app2 }      # labels of the Pods it serves
  ports:
    - port: 80                 # Service port
      targetPort: 80           # container port (nginx)

Without type it is ClusterIP: an IP internal to the cluster, not directly reachable from outside. The Service does not route by Host — it only selects and balances. External access comes from the Ingress.

3. Labels and selectors — the glue

Three places carry the same label app: app2:

Deployment.spec.selector.matchLabels.app        = app2   ← which Pods it manages
Deployment.spec.template.metadata.labels.app   = app2   ← label of created Pods
Service.spec.selector.app                       = app2   ← which Pods get traffic

If the Service selector does not match the real Pod labels, the Service is left with an empty Endpoints list → the object exists but "serves nobody".

4. Ingress and Traefik — host routing

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata: { name: apps }
spec:
  ingressClassName: traefik
  rules:
    - host: app1.com      → service app1     # NAMED rule
    - host: app2.com      → service app2
    - http:               → service app3     # rule WITHOUT host = default backend (catch-all)
  • Who routes: Traefik, the Ingress controller K3s ships by default (exposed on node port 80 via servicelb).
  • The key of the subject: a rule without host acts as the default backend. "Any other Host → app3".
  • No DNS: every curl goes to 192.168.56.110; Traefik decides by the Host header. The host's /etc/hosts only exists for browser testing.

5. The full request journey (the plan's practice)

curl -H "Host: app2.com" http://192.168.56.110
  │
  ├─ 1. Host opens TCP to 192.168.56.110:80 (fixed IP, no DNS)
  ├─ 2. Enters via K3s servicelb (klipper) → Traefik
  ├─ 3. Traefik reads Host: app2.com → Ingress rule → Service app2:80
  ├─ 4. Service app2 (ClusterIP) → kube-proxy picks 1 of its 3 Endpoints (IPVS)
  └─ 5. nginx on the Pod replies "pod: app2-xxxx-yyyy" ($hostname)

The actual balancing is done by kube-proxy (IPVS/iptables tables on the node), not the Service. Repeating the curl exposes the round-robin:

for i in 1 2 3 4 5 6; do curl -s -H "Host: app2.com" http://192.168.56.110 | grep pod; done
# pod: app2-6f9f6f7b57-abcde   ← changes Pod on every request
# pod: app2-8c2f8d5a4b-qwert

Predictions and exercises

Exercise 3.1 — $hostname and the load-balancing proof

What value does $hostname take on the page served by nginx, and why does it prove the balancing of app2?

Show answer

$hostname is an nginx variable that resolves to the container hostname. In Kubernetes that hostname is the Pod name, which the ReplicaSet generates unique: app2-6f9f6f7b57-abcde. Since the 3 replicas have Pods with distinct names, repeating the curl changes the name in the response → that is the live proof that the Service spreads traffic across the 3.

for i in 1 2 3 4 5 6; do curl -s -H "Host: app2.com" http://192.168.56.110 | grep pod; done

Exercise 3.2 — Service with a broken selector

If Service app2 had selector: { app: app2-wrong } (a label no Pod has), what would the user see, and with which command do you check it?

Show answer

The Service is left with an empty Endpoints list → the object exists but serves nobody.

kubectl get endpoints app2      # empty ENDPOINTS  ← the definitive proof
kubectl describe svc app2       # see the selector
kubectl get pods -l app=app2    # do the Pods have that label?

The user gets 503 Service Unavailable (not 502): 503 is "the service exists but has no Pods"; 502 would be "there is a backend, but it fails".

Exercise 3.3 — Routing without DNS and the 404

Where does the distinction between app1.com and "anything else" live if the IP is always the same? And why would a rule without a catch-all give a 404?

Show answer
  • The IP only decides which machine is reached; the distinction lives in the HTTP Host header that Traefik reads and compares against the Ingress rules. There is no DNS in the curl.
  • If there is no rule for that Host and no hostless rule exists, Traefik answers 404: no rule handles that name. The catch-all turns a "potential 404" into app3.

Exercise 3.4 — Seeing the balancing

Which two commands show that the 3 Pods of app2 exist and that the Service knows them?

Show answer 
kubectl get pods -o wide          # 3 app2 Pods (unique names)
kubectl get endpoints app2        # IPs behind Service app2 (3 endpoints)

The Pods are kept alive by the ReplicaSet; the Service publishes its IP list in Endpoints; kube-proxy programs it into iptables/IPVS for balancing.

Exercise 3.5 — The flipped defense question

"app1.com works but a made-up Host falls into app3. Is the DNS broken? Would you add a rule?"

Show answer

It is not a bug, it is the subject's design: "any other Host → app3". No DNS is involved with curl (fixed IP + header). You do not add a rule — the catch-all (hostless rule) is exactly what the requirement asks for; adding one would break "everything not covered goes to app3". It is a default backend rule, not a bug.

Frequent mistakes
  • Confusing port (Service port) with targetPort (container port).
  • Thinking the Service routes by host — no, the Ingress routes; the Service only selects and balances.
  • Thinking $hostname is a shell variable; it is nginx's, and equals the Pod name.
  • Service selector not matching the Deployment template labels → Service with no Endpoints → 503.
  • Believing app3 is DNS — it is the Ingress rule without host.
  • Diagnosing 404/502/503 without first checking kubectl get endpoints and kubectl describe ingress.
