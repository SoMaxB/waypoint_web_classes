Objetivo

Cerrar el curso integrando todo: defender el proyecto completo en orden, saber qué enseñar y justificar en cada parte, y diagnosticar los fallos que un evaluador puede provocar o que ocurren en vivo. Al terminar, pasar de "reproducir comandos" a explicar el porqué detrás de cada capa.

1. La regla de oro de la defensa

Punto de partida

El evaluador tiene el subject delante y tu repo. La evaluación se hace en tu máquina, en vivo. Todo lo que muestres debe salir de ejecutar el repo desde cero.

  • Reproducibilidad por encima de todo: cada parte tiene un solo comando de arranque, un solo comando de verificación y un solo comando de limpieza. Si "funciona pero no sé por qué", es un riesgo; si "falla pero lo sé diagnosticar", es un punto a favor.
  • No leas de los apuntes: cada verificación debe poder explicarse con una frase (qué mando y qué espero).
  • Nombra las decisiones de diseño: en cada parte hay decisiones llamativas (equivalen a "¿por qué está hecho así?" del evaluador).

3. Qué enseñar en cada parte (+ justificaciones)

3.1 p1 — K3s y Vagrant

Qué enseñar: el Vagrantfile (2 VM, config.vm.define, red privada fija, box generic/ubuntu2204), el token compartido en vez de copiar el node-token, y los flags de K3s.

Decisiones a justificar:

  • Token fijo en el Vagrantfile: el worker se une sin leer el fichero node-token generado por K3s (/var/lib/rancher/k3s/server/node-token). Se define un token igual en ambos y se pasa por variable de entorno.
  • --flannel-iface resuelto por IP, no hardcodeado: el NIC de la red privada se llama distinto según provider (eth1, enp0s8...), así que se busca la interfaz a partir de la IP fija (ip -o -4 addr show | grep -w $IP).
  • --node-ip, --advertise-address, --tls-san, --write-kubeconfig-mode=644: cada flag resuelve un problema real (saber "sin él qué pasa/no funciona").
  • Synced folders deshabilitadas: los provisioners file/shell suben lo que el guest necesita; no existe /vagrant.

Verificación: vagrant ssh ravazqueS -c "kubectl get nodes -o wide" → ravazques y ravazquesw, ambos Ready. No hace falta pedir permiso: la verificación se hace pidiendo "demuestre 2 nodos".

3.2 p2 — 3 apps + Ingress

Qué enseñar: los 3 objetos de cada appN.yaml (ConfigMap = configuración/página, Deployment → ReplicaSet → Pod, Service ClusterIP), labels/selectors, y la regla del Ingress sin host para app3.

Decisiones a justificar:

  • La página vive en un ConfigMap de nginx (return 200 + $hostname): no hace falta imagen propia ni volumen con HTML, y $hostname muestra el nombre del Pod → prueba el balanceo.
  • Ingress sin host = default backend (app3, "any other Host"): no es un fallo ni DNS, es el diseño que pide el subject.
  • app2 con 3 réplicas (subject: "una con 3 réplicas"); las demás con 1.
  • Las esperas del script: kubectl wait node y rollout status porque K3s devuelve el control antes de estar listo y Traefik se instala con un Job de Helm en el arranque.

Verificación: bucle de curls a app2.com y mostrar que cambia el pod en cada respuesta (round-robin real vía kube-proxy, no "configurado").

3.3 p3 — K3d + Argo CD + GitHub

Qué enseñar: K3s vs K3d, el cluster iot recreado desde cero, los namespaces argocd/dev, la Application CRD (source/destination/syncPolicy) y el desplegable v1→v2.

Decisiones a justificar:

  • K3d en vez de K3s: cluster desechable dentro de Docker, reproducción en un minuto; el subject p3 pide "without Vagrant".
  • kubectl apply --server-side para instalar Argo CD: las CRDs grandes superan el límite de 262144 bytes de la anotación last-applied-configuration.
  • --dry-run=client -o yaml | kubectl apply -f - para namespaces: hace el create idempotente.
  • prune + selfHeal: Git manda; borrar en Git limpia el cluster, editar a mano se revierte.
  • Los manifests de la app viven en el repo remoto (GitOps): editar local no despliega.

Verificación (la más visual): cambiar v1 → v2 en deployment.yaml, push, sync manual (patch --operation) y curl localhost:8888 devuelve v2; kubectl get application -n argocd muestra Synced/Healthy.

3.4 bonus — GitLab local

Qué enseñar: GitLab como pod dentro de K3d (namespace gitlab), PVCs + Recreate, la automatización vía API en gitlab.sh y la Application con el repoURL interno.

Decisiones a justificar:

  • repoURL = DNS del Service (gitlab.gitlab.svc.cluster.local) y no localhost:8081: Argo CD corre dentro del cluster; el port-forward solo existe en tu host. (Pregunta estrella.)
  • strategy: Recreate: PVCs ReadWriteOnce → un solo escritor; RollingUpdate montaría el mismo disco en dos pods.
  • Idempotencia: extrae y reusa el token de API de un Secret; reusa el cluster iot en vez de recrearlo. "Parte 3 más GitLab", no un segundo lab.
  • gitlab.sh hace todo por API (token con Rails runner, proyecto público, push de manifests): sin clicks en la UI.

Verificación: imprimir el spec.source.repoURL de la Application y cambiar v1→v2 desde GitLab (clone + push) para ver el mismo flujo sin GitHub.

5. Troubleshooting — los 7 escenarios del plan

Cada escenario: síntoma → diagnóstico en orden → causa → arreglo. Prioridad 1: mirar eventos y status antes de "reinstalar todo".

5.1 El worker de p1 no aparece como Ready

síntoma: kubectl get nodes  →  ravazquesw  NotReady / falta el nodo
vagrant ssh ravazqueS  -c "kubectl get nodes -o wide"
vagrant ssh ravazqueSW -c "systemctl status k3s-agent"        # ¿arrancó?
vagrant ssh ravazqueSW -c "journalctl -u k3s-agent -n 50"      # ¿por qué falla?
  • ¿No existe el nodo? el agente no llegó a registrarse → mirar logs de k3s-agent; token incorrecto → 403/401 (Bootstrap already done?) en journal.
  • ¿Existe pero NotReady? el kubelet no está listo → IP/interfaz mal (--node-ip no coincide con la red privada, o --flannel-iface apunta a eth0/NAT en vez de a la privada).
  • ¿connection refused al API server desde el worker? la IP del server no es alcanzable por la red privada o no se usó --tls-san.

5.2 kubectl da connection refused (o el API server no responde)

  • En p1/p2: ¿VM viva? (vagrant status, vagrant up) ¿K3s corriendo? (systemctl status k3s). ¿KUBECONFIG apunta a /etc/rancher/k3s/k3s.yaml? ¿El certificado válido para la IP? (--tls-san).
  • En p3/bonus: ¿cluster iot existe? (k3d cluster list) ¿contexto correcto? (kubectl config current-context — k3d kubeconfig merge ... --kubeconfig-switch-context). ¿Docker arriba? (sin Docker, el cluster K3d no arranca).
vagrant status                        # p1/p2: ¿VMs Running?
k3d cluster list                       # p3/bonus: ¿existe iot?
kubectl config current-context         # ¿estoy contra el cluster esperado?
docker info                            # p3/bonus: base de K3d

5.3 p2 devuelve 404

síntoma: curl -H "Host: appX.com" http://192.168.56.110 → 404
kubectl describe ingress apps          # ¿existe la regla para ese Host?
kubectl get ingress -o yaml            # ¿faltó el catch-all (regla sin host)?

404 = regla que falta (no backend roto). Host sin host en el Ingress y sin default → Traefik no sabe a dónde; 404 es su respuesta honesta.

5.4 p2 devuelve 502 o 503

kubectl get pods -o wide               # ¿Pods Running? ¿CrashLoop?
kubectl get endpoints                  # ¿el Service tiene IPs detrás?
kubectl describe svc appX              # selector del Service
kubectl -n kube-system rollout status deploy/traefik

502 = el backend existe pero falla (Pods rotos, imagen no disponible, Traefik aún instalándose). 503 = el backend no existe (Service sin Endpoints: selector que no coincide con ningún Pod). Regla mental: 404 regla · 502 backend roto · 503 sin endpoints.

5.5 Argo CD queda en OutOfSync o ComparisonError

kubectl -n argocd get application playground -o yaml   # status.operationState, conditions
kubectl -n argocd get application playground            # Sync/Health compacto
kubectl logs -n argocd deploy/argocd-repo-server --tail=50
  • OutOfSync = cambio en el repo aún no aplicado (normal tras un push sin sync manual) → kubectl -n argocd patch application playground --type merge -p '{"operation":{"sync":{"revision":"HEAD"}}}' o esperar el poll (~3 min).
  • ComparisonError = Argo CD no puede leer el repo: repoURL mal, path que no existe (ojo: relativo a la raíz del repo), rama mal (p3 usa HEAD, bonus main), repo privado sin credenciales, o el repo (GitLab bonus) no está aún sano. → arreglar application.yaml y reaplicar.

5.6 GitLab tarda demasiado o reinicia

kubectl -n gitlab get pods              # ¿Starting / CrashLoopBackOff?
kubectl -n gitlab logs deploy/gitlab --tail=50
kubectl -n gitlab describe pod gitlab-xxx   # eventos: ¿OOM? ¿migraciones?
free -h; docker info                   # ¿RAM/Docker suficiente?
  • Primer boot = reconfigure + migraciones (10-20 min; el rollout status espera 30 min). Sobreesperar es normal, no es un bug.
  • Reinicios por OOMKilled → falta RAM (el script avisa por debajo de 8 GiB). Reinicios por probes → revisar monitoring_whitelist (si /-/health da 403/404, el kubelet nunca ve al pod Ready).
  • Reusar el cluster: si k3d cluster start iot tras un stop, GitLab tarda varios minutos en volver a estar healthy.

5.7 Docker no responde

docker info                            # ¿Daemon reachable?
systemctl status docker                # ¿servicio arriba?
sudo systemctl start docker            # si está parado
sudo usermod -aG docker $USER          # si error de permisos → cerrar sesión

p3 y bonus requieren Docker; sin él k3d cluster create falla. El preflight de install.sh ya avisa con mensajes orientativos. Los errores de permisos son del grupo docker (re-login).

Predicciones y ejercicios

Ejercicio 6.1 — Worker NotReady

El worker de p1 existe como nodo pero está NotReady. Nombra las 3 causas más probables y cómo probarlas sin reinstalar.

Mostrar solución
  1. Interface equivocada en Flannel (--flannel-iface sobre el NIC de NAT en vez de la red privada) → el pod network no converge. Mirar journalctl -u k3s-agent y verificar la IP: ip -o -4 addr show.
  2. --node-ip que no coincide con el rango de la red privada → el kubelet se registra con una IP inalcanzable para el server.
  3. Recursos mínimos (1 CPU/1 GiB, o el host saturado) → el kubelet no termina de arrancar.

Prueba sin reinstalar: vagrant ssh ravazqueSW -c "systemctl status k3s-agent" + logs; en el server kubectl describe node ravazquesw para ver las conditions/mensajes; kubectl get node ravazquesw -o yaml para ver NodeAddresses y kubeletReady.

Ejercicio 6.2 — 404 vs 502 vs 503 en p2

Un evaluador te pide: "rompe un selector y muéstrame qué pasa". ¿Qué comando y qué respuesta esperas?

Mostrar solución

Cambiar Service.spec.selector a una label que ningún Pod tiene y reaplicar:

kubectl -n dev edit svc app2   # selector.app: app2 → app2-wrong
curl -H "Host: app2.com" http://192.168.56.110   # 503 Service Unavailable
kubectl get endpoints app2      # Endpoints vacío (la prueba definitiva)
kubectl get pods -l app=app2    # confirmar que los Pods NO llevan esa label

Es 503 (backend no existe), no 502. Recordar: prune/selfHeal no aplican en p2 (no hay Argo CD): el cambio a mano permanece hasta que restaures el selector — es el contraste perfecto con p3.

Ejercicio 6.3 — 502 con pods Running

En p2 todos los pods están Running y el Service tiene Endpoints, pero curl app1.com devuelve 502. ¿Qué revisas?

Mostrar solución

502 = "hay backend pero falla el enrutado/proxy". Primero a Traefik: kubectl -n kube-system rollout status deploy/traefik y logs (kubectl -n kube-system logs deploy/...). Si Traefik acabó de instalarse, puede tardar en Ready. Segundo, comprobar que el targetPort coincide con el puerto del contenedor (port del Service vs containerPort): un desajuste da 502 porque el proxy fija el backend pero el Pod no escucha en ese puerto. Tercero, verificar que el pod responde internamente: kubectl exec deploy/app1 -- wget -qO- http://localhost/.

Ejercicio 6.4 — Argo CD OutOfSync "para siempre"

Cambié v1→v2 en el repo, el push fue bien, pero kubectl get application muestra OutOfSync y nunca pasa. ¿Qué hago en orden?

Mostrar solución
  1. Comprobar que el push llegó al repo correcto y a la rama correcta (git remote -v; targetRevision = HEAD en p3 → rama default, main en bonus). Un push a una rama que Argo no mira = eterno OutOfSync.
  2. Forzar el sync: kubectl -n argocd patch application playground --type merge -p '{"operation":{"sync":{"revision":"HEAD"}}}'.
  3. Mirar status.operationState en -o yaml para ver el error del último intento (mensajes de git, del manifests deseado...).
  4. Si sigue, argocd app get playground -n argocd (CLI) suele dar la diff y el error con más contexto; y kubectl logs argocd-repo-server.

Regla mental: OutOfSync con intención ≠ rotura; es Argo diciendo "hay estado deseado distinto". Rotura sería ComparisonError.

Ejercicio 6.5 — demo GitOps con selfHeal

Muéstrame que Argo CD "manda" en el cluster. ¿Qué hago y qué debería pasar?

Mostrar solución
  1. kubectl -n dev scale deploy playground --replicas=5 (o kubectl edit).
  2. Esperar al siguiente ciclo de Argo (≤ ~3 min): kubectl get deploy playground -n dev -w (verás 5 → vuelta a 1).
  3. Autoridad de diagnóstico: la Application es Synced y selfHeal: true → el controlador revierte la deriva a lo que Git dice (replicas: 1).

En el mismo momento puedes demostrar prune: borra el Deployment desde el cluster y Argo lo recrea; borra un objeto del repo remoto y Argo lo elimina del cluster. Git es la única fuente de verdad.

Ejercicio 6.6 — La pregunta abierta de "estructura del repo"

¿Por qué p1/p2 tienen Vagrantfile, p3/bonus no, y por qué confs y scripts separados?

Mostrar solución
  • Vagrantfile solo en p1/p2: el subject obliga a VMs (Vagrant) en las partes 1 y 2; p3 y el bonus van sin Vagrant (K3d sobre Docker, "without this time"), solo scripts. Mantenerlos separados deja ver esa frontera de arquitectura.
  • scripts vs confs: scripts = comportamiento (instalación, esperas, API); confs = declaración (YAML de los objetos). El subject exige ambas carpetas ("Any scripts you need... The configuration files in a confs folder") y facilita el copy/paste de manifiestos a un repo GitOps (p3/bonus) sin arrastrar lógica.
  • srcs/ raíz: el subject pide p1, p2, p3, bonus en la raíz del repo; este repo los agrupa bajo srcs/ respetando esos cuatro nombres (la defensa muestra find -maxdepth 2).

Ejercicio 6.7 — La demo "todo desde cero"

El evaluador pide levantar todo de nuevo. ¿En qué orden y qué depende de qué?

Mostrar solución
  1. p1 (VMs server+worker) → vagrant up --provider=libvirt (o virtualbox) desde srcs/p1. Verificar 2 nodos. vagrant destroy -f al terminar si siguen p2/bonus (recursos).
  2. p2 (1 VM) → vagrant up desde srcs/p2. Verificar curls por Host. vagrant destroy -f antes de bonus (RAM).
  3. p3 (host, Docker) → ./scripts/install.sh (borra y recrea iot). Verificar ns + app + v1.
  4. bonus (host, Docker) → ./scripts/install.sh (reusa iot si existe, crea ns gitlab, instala/reusa Argo). Verificar repoURL + v1→v2 desde GitLab.

Dependencias: p1 y p2 no dependen de nada previo (se levantan solas); p3 no necesita las VMs; el bonus asume Docker y puede reusar el cluster dejado por p3. Con p1/p2 encendidas + Docker + bonus => memoria justa: el README del bonus pide destruir las VMs primero.

Errores frecuentes en defensa
  • Confundir p3 y bonus en la demo: si vas a defender bonus, haz el flujo v1→v2 desde GitLab, no reusando GitHub.
  • Correr p1/p2 a la vez que bonus: la RAM se agota y GitLab muere por OOM; destruye las VMs.
  • No tocar el repo en p3: "cambiar en local" en la defensa no despliega; hay que hacer push (o sync manual del cambio ya subido).
  • Diagnosticar sin mirar status/events: kubectl describe y journalctl contestan antes que reinstalar.
  • Leer de apuntes: si el evaluador pide "muéstrame dónde está el token", saber decir "en el Vagrantfile de p1, y lo paso como variable de entorno" sin abrir el fichero.
  • Creer que el 404 es DNS: en p2 no hay DNS; es falta de regla en el Ingress (o catch-all).
  • No justificar balances de p3/bonus: la demo v1→v2 tiene que terminar en el curl mostrando el tag nuevo, no en "intenté el sync".

Objective

Close the course by integrating everything: defend the whole project in order, know what to teach and justify in each part, and diagnose the failures an evaluator may trigger or that happen live. By the end, move from "reproducing commands" to explaining the why behind each layer.

1. The golden rule of the defense

Starting point

The evaluator has the subject in front of them and your repo. The evaluation runs live on your machine. Everything you show must come from running the repo from scratch.

  • Reproducibility above all: each part has one start command, one verification command and one cleanup command. If it "works but I do not know why", that is a risk; if it "fails but I can diagnose it", that is a point in your favor.
  • Do not read from notes: every verification must be explainable in one sentence (what I run and what I expect).
  • Name the design decisions: each part has striking decisions (they answer the evaluator's "why is it built this way?").

3. p3   → K3d + Argo CD + GitHub, v1→v2 proof

3. What to teach in each part (+ justifications)

3.1 p1 — K3s and Vagrant

What to teach: the Vagrantfile (2 VMs, config.vm.define, fixed private network, box generic/ubuntu2204), the shared token instead of copying the node-token, and the K3s flags.

Decisions to justify:

  • Fixed token in the Vagrantfile: the worker joins without reading the node-token file generated by K3s (/var/lib/rancher/k3s/server/node-token). An identical token is defined on both and passed via an environment variable.
  • --flannel-iface resolved from the IP, not hardcoded: the private-network NIC has a different name per provider (eth1, enp0s8...), so the interface is looked up from the fixed IP (ip -o -4 addr show | grep -w $IP).
  • --node-ip, --advertise-address, --tls-san, --write-kubeconfig-mode=644: each flag solves a real problem (know "without it what breaks/fails").
  • Synced folders disabled: the file/shell provisioners upload what the guest needs; there is no /vagrant.

Verification: vagrant ssh ravazqueS -c "kubectl get nodes -o wide" → ravazques and ravazquesw, both Ready. You do not need to ask permission: the verification is done by asking "show me 2 nodes".

3.2 p2 — 3 apps + Ingress

What to teach: the 3 objects of each appN.yaml (ConfigMap = config/page, Deployment → ReplicaSet → Pod, ClusterIP Service), labels/selectors, and the Ingress rule without a host for app3.

Decisions to justify:

  • The page lives in an nginx ConfigMap (return 200 + $hostname): no custom image or HTML volume needed, and $hostname shows the Pod name → proves the balancing.
  • Ingress without host = default backend (app3, "any other Host"): it is not a bug or DNS, it is the design the subject asks for.
  • app2 with 3 replicas (subject: "one with 3 replicas"); the others with 1.
  • The script's waits: kubectl wait node and rollout status because K3s returns control before it is ready and Traefik is installed by a Helm Job at startup.

Verification: loop curls to app2.com and show the pod changes on each response (real round-robin via kube-proxy, not "configured").

3.3 p3 — K3d + Argo CD + GitHub

What to teach: K3s vs K3d, the iot cluster recreated from scratch, the argocd/dev namespaces, the Application CRD (source/destination/syncPolicy) and the v1→v2 deployable.

Decisions to justify:

  • K3d instead of K3s: a disposable cluster inside Docker, reproduced in a minute; p3's subject says "without Vagrant".
  • kubectl apply --server-side to install Argo CD: the big CRDs overflow the 262144-byte limit of the last-applied-configuration annotation.
  • --dry-run=client -o yaml | kubectl apply -f - for namespaces: makes the create idempotent.
  • prune + selfHeal: Git rules; deleting in Git cleans the cluster, manual edits get reverted.
  • The app manifests live in the remote repo (GitOps): editing locally does not deploy.

Verification (the most visual): change v1 → v2 in deployment.yaml, push, manual sync (patch --operation) and curl localhost:8888 returns v2; kubectl get application -n argocd shows Synced/Healthy.

3.4 bonus — local GitLab

What to teach: GitLab as a pod inside K3d (namespace gitlab), PVCs + Recreate, the API automation in gitlab.sh and the Application with the internal repoURL.

Decisions to justify:

  • repoURL = Service DNS (gitlab.gitlab.svc.cluster.local) and not localhost:8081: Argo CD runs inside the cluster; the port-forward only exists on your host. (Star question.)
  • strategy: Recreate: PVCs are ReadWriteOnce → a single writer; RollingUpdate would mount the same disk in two pods.
  • Idempotency: it extracts and reuses the API token from a Secret; it reuses cluster iot instead of recreating it. "Part 3 plus GitLab", not a second lab.
  • gitlab.sh does everything via API (token with the Rails runner, public project, manifests push): no UI clicks.

Verification: print the Application's spec.source.repoURL and change v1→v2 from GitLab (clone + push) to see the same flow without GitHub.

5. Troubleshooting — the 7 scenarios of the plan

Each scenario: symptom → diagnosis in order → cause → fix. Priority 1: look at events and status before "reinstalling everything".

5.1 The p1 worker does not show as Ready

symptom: kubectl get nodes  →  ravazquesw  NotReady / node missing
vagrant ssh ravazqueS  -c "kubectl get nodes -o wide"
vagrant ssh ravazqueSW -c "systemctl status k3s-agent"        # did it start?
vagrant ssh ravazqueSW -c "journalctl -u k3s-agent -n 50"      # why does it fail?
  • Node missing? the agent never registered → look at the k3s-agent logs; wrong token → 403/401 (Bootstrap already done?) in the journal.
  • Exists but NotReady? the kubelet is not ready → wrong IP/interface (--node-ip not matching the private network, or --flannel-iface pointing at eth0/NAT instead of the private one).
  • connection refused to the API server from the worker? the server IP is not reachable over the private network or --tls-san was not used.

5.2 kubectl gives connection refused (or the API server does not answer)

  • In p1/p2: is the VM alive? (vagrant status, vagrant up) Is K3s running? (systemctl status k3s). Does KUBECONFIG point to /etc/rancher/k3s/k3s.yaml? Is the certificate valid for the IP? (--tls-san).
  • In p3/bonus: does cluster iot exist? (k3d cluster list) Is the context right? (kubectl config current-context — k3d kubeconfig merge ... --kubeconfig-switch-context). Is Docker up? (without Docker the K3d cluster does not start).
vagrant status                        # p1/p2: VMs Running?
k3d cluster list                       # p3/bonus: does iot exist?
kubectl config current-context         # am I against the expected cluster?
docker info                            # p3/bonus: the base of K3d

5.3 p2 returns 404

symptom: curl -H "Host: appX.com" http://192.168.56.110 → 404
kubectl describe ingress apps          # does a rule exist for that Host?
kubectl get ingress -o yaml            # is the catch-all (hostless rule) missing?

404 = a missing rule (not a broken backend). A Host with no rule in the Ingress and no default → Traefik does not know where to go; 404 is its honest answer.

5.4 p2 returns 502 or 503

kubectl get pods -o wide               # Pods Running? CrashLoop?
kubectl get endpoints                  # does the Service have IPs behind it?
kubectl describe svc appX              # Service selector
kubectl -n kube-system rollout status deploy/traefik

502 = the backend exists but fails (broken Pods, unavailable image, Traefik still installing). 503 = the backend does not exist (Service without Endpoints: a selector matching no Pod). Mental rule: 404 rule · 502 broken backend · 503 no endpoints.

5.5 Argo CD stuck in OutOfSync or ComparisonError

kubectl -n argocd get application playground -o yaml   # status.operationState, conditions
kubectl -n argocd get application playground            # compact Sync/Health
kubectl logs -n argocd deploy/argocd-repo-server --tail=50
  • OutOfSync = a change in the repo not applied yet (normal after a push without manual sync) → kubectl -n argocd patch application playground --type merge -p '{"operation":{"sync":{"revision":"HEAD"}}}' or wait for the poll (~3 min).
  • ComparisonError = Argo CD cannot read the repo: wrong repoURL, path that does not exist (note: relative to the repo root), wrong branch (p3 uses HEAD, bonus main), private repo without credentials, or the repo (bonus GitLab) not healthy yet. → fix application.yaml and reapply.

5.6 GitLab is too slow or restarts

kubectl -n gitlab get pods              # Starting / CrashLoopBackOff?
kubectl -n gitlab logs deploy/gitlab --tail=50
kubectl -n gitlab describe pod gitlab-xxx   # events: OOM? migrations?
free -h; docker info                   # enough RAM/Docker?
  • First boot = reconfigure + migrations (10-20 min; the rollout status waits 30 min). Over-waiting is normal, not a bug.
  • Restarts from OOMKilled → not enough RAM (the script warns below 8 GiB). Restarts from probes → check monitoring_whitelist (if /-/health gives 403/404, the kubelet never sees the pod as Ready).
  • Reusing the cluster: after k3d cluster start iot following a stop, GitLab takes several minutes to become healthy again.

5.7 Docker does not respond

docker info                            # is the daemon reachable?
systemctl status docker                # is the service up?
sudo systemctl start docker            # if it is stopped
sudo usermod -aG docker $USER          # on permission errors → re-login

p3 and bonus require Docker; without it k3d cluster create fails. install.sh's preflight already warns with helpful messages. Permission errors come from the docker group (re-login).

Predictions and exercises

Exercise 6.1 — Worker NotReady

The p1 worker exists as a node but is NotReady. Name the 3 most likely causes and how to test them without reinstalling.

Show answer
  1. Wrong Flannel interface (--flannel-iface on the NAT NIC instead of the private network) → the pod network never converges. Look at journalctl -u k3s-agent and verify the IP: ip -o -4 addr show.
  2. --node-ip not matching the private network range → the kubelet registers with an IP the server cannot reach.
  3. Minimum resources (1 CPU/1 GiB, or a saturated host) → the kubelet never finishes starting.

Test without reinstalling: vagrant ssh ravazqueSW -c "systemctl status k3s-agent" + logs; on the server kubectl describe node ravazquesw to see conditions/messages; kubectl get node ravazquesw -o yaml for NodeAddresses and kubeletReady.

Exercise 6.2 — 404 vs 502 vs 503 in p2

An evaluator asks: "break a selector and show me what happens". Which command and which response do you expect?

Show answer

Change Service.spec.selector to a label no Pod has and reapply:

kubectl -n dev edit svc app2   # selector.app: app2 → app2-wrong
curl -H "Host: app2.com" http://192.168.56.110   # 503 Service Unavailable
kubectl get endpoints app2      # empty Endpoints (the definitive proof)
kubectl get pods -l app=app2    # confirm the Pods do NOT carry that label

It is 503 (backend missing), not 502. Remember: prune/selfHeal do not apply in p2 (no Argo CD): the manual change persists until you restore the selector — the perfect contrast with p3.

Exercise 6.3 — 502 with Running pods

In p2 all pods are Running and the Service has Endpoints, but curl app1.com returns 502. What do you check?

Show answer

502 = "there is a backend but routing/proxy fails". First, Traefik: kubectl -n kube-system rollout status deploy/traefik and logs (kubectl -n kube-system logs deploy/...). If Traefik just installed, it may take time to be Ready. Second, check that targetPort matches the container port (Service port vs containerPort): a mismatch gives 502 because the proxy fixes the backend but the Pod does not listen on that port. Third, verify the pod answers internally: kubectl exec deploy/app1 -- wget -qO- http://localhost/.

Exercise 6.4 — Argo CD stuck "forever" in OutOfSync

You changed v1→v2 in the repo, the push went well, but kubectl get application shows OutOfSync and never progresses. What do you do in order?

Show answer
  1. Check the push landed on the right repo and the right branch (git remote -v; targetRevision = HEAD in p3 → default branch, main in bonus). A push to a branch Argo does not watch = eternal OutOfSync.
  2. Force the sync: kubectl -n argocd patch application playground --type merge -p '{"operation":{"sync":{"revision":"HEAD"}}}'.
  3. Look at status.operationState with -o yaml to see the last attempt's error (git messages, desired manifests...).
  4. If it persists, argocd app get playground -n argocd (CLI) usually gives the diff and the error with more context; and kubectl logs argocd-repo-server.

Mental rule: OutOfSync with intent ≠ breakage; it is Argo saying "there is a different desired state". Breakage would be ComparisonError.

Exercise 6.5 — GitOps demo with selfHeal

Show me that Argo CD "rules" the cluster. What do I do and what should happen?

Show answer
  1. kubectl -n dev scale deploy playground --replicas=5 (or kubectl edit).
  2. Wait for Argo's next cycle (≤ ~3 min): kubectl get deploy playground -n dev -w (you will see 5 → back to 1).
  3. Diagnostic authority: the Application is Synced and selfHeal: true → the controller reverts the drift to what Git says (replicas: 1).

In the same moment you can demonstrate prune: delete the Deployment from the cluster and Argo recreates it; delete an object from the remote repo and Argo removes it from the cluster. Git is the only source of truth.

Exercise 6.6 — The open "repo structure" question

Why do p1/p2 have a Vagrantfile and p3/bonus do not, and why are confs and scripts separated?

Show answer
  • Vagrantfile only in p1/p2: the subject mandates VMs (Vagrant) in parts 1 and 2; p3 and bonus go without Vagrant (K3d over Docker, "without this time"), scripts only. Keeping them apart exposes that architecture boundary.
  • scripts vs confs: scripts = behavior (installation, waits, API); confs = declaration (the objects' YAML). The subject demands both folders ("Any scripts you need... The configuration files in a confs folder") and eases copy/pasting manifests into a GitOps repo (p3/bonus) without dragging logic.
  • srcs/ root: the subject asks for p1, p2, p3, bonus at the repo root; this repo groups them under srcs/ keeping those four names (the defense shows find -maxdepth 2).

Exercise 6.7 — The "everything from scratch" demo

The evaluator asks to bring everything up again. In what order, and what depends on what?

Show answer
  1. p1 (server+worker VMs) → vagrant up --provider=libvirt (or virtualbox) from srcs/p1. Verify 2 nodes. vagrant destroy -f when done if p2/bonus follow (resources).
  2. p2 (1 VM) → vagrant up from srcs/p2. Verify the per-Host curls. vagrant destroy -f before bonus (RAM).
  3. p3 (host, Docker) → ./scripts/install.sh (deletes and recreates iot). Verify ns + app + v1.
  4. bonus (host, Docker) → ./scripts/install.sh (reuses iot if it exists, creates ns gitlab, installs/reuses Argo). Verify repoURL + v1→v2 from GitLab.

Dependencies: p1 and p2 do not depend on anything prior (they come up on their own); p3 does not need the VMs; bonus assumes Docker and may reuse the cluster left by p3. With p1/p2 on + Docker + bonus => tight memory: the bonus README asks you to destroy the VMs first.

Frequent defense mistakes
  • Confusing p3 and bonus in the demo: if you are defending bonus, do the v1→v2 flow from GitLab, not reusing GitHub.
  • Running p1/p2 at the same time as bonus: RAM runs out and GitLab dies from OOM; destroy the VMs.
  • Not touching the repo in p3: "changing locally" in the defense does not deploy; you must push (or manually sync the already-pushed change).
  • Diagnosing without looking at status/events: kubectl describe and journalctl answer before reinstalling.
  • Reading from notes: if the evaluator asks "show me where the token is", know how to say "in p1's Vagrantfile, passed as an environment variable" without opening the file.
  • Believing the 404 is DNS: in p2 there is no DNS; it is a missing Ingress rule (or catch-all).
  • Not justifying the p3/bonus flows: the v1→v2 demo must end with the curl showing the new tag, not with "I tried the sync".
