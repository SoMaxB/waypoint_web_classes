Clase 2 · Vagrant, VM y p1Class 2 · Vagrant, VMs and p1

Vagrant · box · provisioner · K3s · node-token
Objetivo

Entender cómo se levanta un cluster K3s de dos nodos con Vagrant. Al terminar: explicar qué son el Vagrantfile, el provider, la box y los provisioners; unir el worker (<login>SW) al server (<login>S) sin copiar el node-token que genera el instalador de K3s; y justificar cada flag del server.sh del repo.

1. Los ficheros y las capas

En srcs/p1/ hay tres piezas. El Vagrantfile es la receta declarativa: qué máquinas se crean, con qué red y qué provisioners se ejecutan. Los scripts server.sh y worker.sh son el cocinado: qué se instala dentro de cada máquina.

Vagrant         → crea y provisiona las VMs        (orquestador de máquinas)
  └─ server     → control-plane + API server        (<login>S,    192.168.56.110)
  └─ agent      → worker                            (<login>SW,   192.168.56.111)
Los roles de cada fichero
FicheroRol
srcs/p1/VagrantfileReceta declarativa: 2 máquinas, IPs fijas, recursos y provisioners. Ahí vive también el token (sección 2).
srcs/p1/scripts/server.shCocinado del server: instala K3s en modo server (control-plane).
srcs/p1/scripts/worker.shCocinado del worker: instala K3s en modo agent y lo une al server.

2. El token del cluster — el truco central

Cuando el instalador de K3s corre en modo server, genera un token aleatorio y lo guarda en /var/lib/rancher/k3s/server/node-token. El agente necesita ese mismo token para autenticarse. Copiar el fichero entre máquinas obliga a sincronizar (orden de arranque, scp, carpeta compartida) — frágil e innecesario. Además, aquí la synced folder está desactivada.

Solución del repo: fijar el token nosotros en el Vagrantfile y pasárselo a ambos scripts vía args:

K3S_TOKEN = "iot-<login>-k3s-token"

server.vm.provision "shell", path: "scripts/server.sh", args: [SERVER_IP, K3S_TOKEN]
worker.vm.provision "shell", path: "scripts/worker.sh", args: [SERVER_IP, WORKER_IP, K3S_TOKEN]

Por qué funciona: el instalador de K3s respeta la variable de entorno K3S_TOKEN — si existe, no genera uno aleatorio. Server y worker se provisionan con el mismo valor, así que el agente autentica sin copiar ficheros y sin depender del orden de arranque.

Ojo

Este token es de laboratorio, no un secreto real. En producción, K3S_TOKEN vendría de un gestor de secretos, no escrito en un Vagrantfile.

3. Resolver la interfaz desde la IP — el detalle clave

El nombre de la NIC de la red privada cambia según el provider (libvirt/KVM → eth1…, VirtualBox → enp0s8…). Si se hardcodea, solo funciona en una máquina. Como la IP privada sí la fijamos nosotros, se resuelve la interfaz a partir de ella:

IFACE="$(ip -o -4 addr show | grep -w "${SERVER_IP}" | awk '{print $2}' | head -n1)"

Desglose del pipeline:

  • ip -o -4 addr show — una línea por interfaz, solo IPv4.
  • grep -w "${SERVER_IP}" — solo la línea con nuestra IP (coincidencia exacta).
  • awk '{print $2}' — extrae el nombre de la interfaz.
  • head -n1 — defensivo; se queda con la primera.

Ese nombre se pasa a K3s como --flannel-iface: la interfaz por la que la red de Pods (flannel) se comunica entre nodos.

4. Flags del server — para qué sirve cada una

Con el IFACE resuelto, el server se instala así (snippet real del repo):

curl -sfL https://get.k3s.io | K3S_TOKEN="${TOKEN}" INSTALL_K3S_EXEC="server \
  --node-ip=${SERVER_IP} \
  --advertise-address=${SERVER_IP} \
  --flannel-iface=${IFACE} \
  --tls-san=${SERVER_IP} \
  --write-kubeconfig-mode=644" sh -
FlagQué haceSin ella…
--node-ipIP con la que el kubelet se registra como nodo.se registra con la NAT (10.0.2.x); server y worker quedan en mundos separados y flannel se rompe.
--advertise-addressIP que el API server anuncia para que los clientes se conecten.anuncia una IP mala y los clientes no llegan.
--flannel-ifaceinterfaz de la red de Pods (CNI/flannel).apunta a la NAT; los nodos no se ven entre sí.
--tls-sanIP extra incluida en el certificado del API server.el worker falla al validar el cert (x509 … no IP SANs).
--write-kubeconfig-mode=644kubeconfig legible para todos.vagrant no puede leer /etc/rancher/k3s/k3s.yaml sin sudo.

El server.sh remata con un export KUBECONFIG=/etc/rancher/k3s/k3s.yaml añadido al .bashrc del usuario: kubectl funciona sin sudo ni flags raros. No se usa --bind-address: por defecto el API server también escucha en 127.0.0.1, y el kubectl local del server funciona.

5. El worker — un solo concepto nuevo

En el worker solo hay una idea nueva: K3S_URL.

curl -sfL https://get.k3s.io | \
  K3S_URL="https://192.168.56.110:6443" \
  K3S_TOKEN="${TOKEN}" \
  INSTALL_K3S_EXEC="agent \
    --node-ip=192.168.56.111 \
    --flannel-iface=${IFACE}" sh -

K3S_URL le dice al instalador que cree el servicio k3s-agent (y no k3s), y con K3S_TOKEN usa el token fijado en vez de generar otro. El agente es un cliente simple: se conecta a la URL, valida el certificado del server y se registra con --node-ip. No lleva --advertise-address ni --tls-san.

Predicciones y ejercicios

Ejercicio 2.1 — El token del cluster

Estás solo con el Vagrantfile y los scripts. ¿Cómo consigue <login>SW el token sin copiar el node-token? ¿Qué problema elimina esa elección?

Mostrar solución

Forma A (sincronizar): esperar a que el server escriba /var/lib/rancher/k3s/server/node-token y copiarlo (scp/SSH). Problemas: depende del orden de arranque y la carpeta compartida está desactivada.

Forma B (token fijo): definir el token en el Vagrantfile y pasárselo a ambos scripts con args. El instalador usa la env K3S_TOKEN y no genera otro. Sin copias, sin orden.

Ejercicio 2.2 — La interfaz de red

¿Por qué no escribir directamente --flannel-iface=eth1 en ambos scripts?

Mostrar solución

El nombre de la NIC privada lo decide el provider: libvirt la llama eth1, VirtualBox enp0s8… Si se hardcodea, solo funciona en una máquina. La IP privada la fijamos nosotros, así que se resuelve la interfaz con el pipeline ip -o -4 addr show | grep -w "$IP" | awk '{print $2}': el mismo código vale en ambos providers.

Ejercicio 2.4 — Diagnosticar "worker NotReady"

vagrant up terminó, pero kubectl get nodes solo muestra <login>S Ready; <login>SW está en NotReady. Orden de sospechas — de más probable a más rara:

#SospechaQué lo confirma (o lo descarta)Comando
1Flannel / interfazEl worker se registró con la IP de la NAT (10.0.2.x) en vez de 192.168.56.111.kubectl get nodes -o wide · journalctl -u k3s-agent -n 50 · ip -o -4 addr show
2TokenEl agente no autentica (HTTP 401).journalctl -u k3s-agent | grep -i token
3Certificado / TLS SANEl agente no valida el cert ("cannot validate certificate for 192.168.56.110").journalctl -u k3s-agent | grep x509
4Firewall / redNo se llega al puerto 6443 del server.nc -zv 192.168.56.110 6443
Orden mental

flannel → token → certificado → firewall. kubectl get nodes -o wide separa «IP mal puesta» de «nodo sano» en un segundo.

Errores frecuentes
  • Creer que el worker "pide" el token al server en tiempo de ejecución → se pasa por env K3S_TOKEN en los provisioners, constante en el Vagrantfile.
  • Hardcodear la NIC privada en los scripts → se rompe en otro provider.
  • Confundir --node-ip (con qué IP se registra el nodo) con --advertise-address (con qué IP se anuncia el API server).
  • Pensar que --tls-san es una opción del cliente; en realidad rellena las IPs/hostnames del API server en el cert que el agente (y kubectl remoto) validan.
  • Diagnosticar el worker leyendo el server: el log que importa vive en el propio worker (journalctl -u k3s-agent).

Objective

Understand how a two-node K3s cluster is brought up with Vagrant. By the end: explain the Vagrantfile, the provider, the box and the provisioners; join the worker (<login>SW) to the server (<login>S) without copying the K3s-generated node-token; and justify every flag in the repo's server.sh.

1. The files and the layers

In srcs/p1/ there are three pieces. The Vagrantfile is the declarative recipe: which machines are created, with which network and IPs, and which provisioners run. The server.sh and worker.sh scripts are the cooking: what gets installed inside each machine.

Vagrant           → creates and provisions the VMs   (machine orchestrator)
  └─ server       → control-plane + API server       (<login>S,    192.168.56.110)
  └─ agent        → worker                           (<login>SW,   192.168.56.111)
Roles of the files
FileRole
srcs/p1/VagrantfileDeclarative recipe: 2 machines, fixed IPs and provisioners. It also pins the token (section 2).
srcs/p1/scripts/server.shServer cooking: installs K3s in server (control-plane) mode.
srcs/p1/scripts/worker.shWorker cooking: installs K3s in agent mode and joins it to the server.

2. The cluster token — the central trick

When the K3s installer runs in server mode it generates a random token at /var/lib/rancher/k3s/server/node-token. The agent needs that same token to authenticate. Copying the file between machines forces sync (boot order, scp, shared folder) — fragile and unnecessary. Here the synced folder is even disabled.

Repo solution: pin the token ourselves in the Vagrantfile and pass it to both scripts via args:

K3S_TOKEN = "iot-<login>-k3s-token"

server.vm.provision "shell", path: "scripts/server.sh", args: [SERVER_IP, K3S_TOKEN]
worker.vm.provision "shell", path: "scripts/worker.sh", args: [SERVER_IP, WORKER_IP, K3S_TOKEN]

Why it works: the K3s installer honors the K3S_TOKEN environment variable — when present, it does not generate a random one. Server and worker are provisioned with the same value, so the agent authenticates with no file copying and no dependency on boot order.

Heads up

This is a lab token, not a real secret. In production, K3S_TOKEN would come from a secrets manager, not a Vagrantfile.

3. Resolving the interface from the IP — the key detail

The private NIC name changes per provider (libvirt/KVM → eth1…, VirtualBox → enp0s8…). Hardcoding it works on only one machine. Since the private IP is something we fix ourselves, the interface is resolved from it:

IFACE="$(ip -o -4 addr show | grep -w "${SERVER_IP}" | awk '{print $2}' | head -n1)"

Pipeline breakdown:

  • ip -o -4 addr show — one line per interface, IPv4 only.
  • grep -w "${SERVER_IP}" — only the line with our IP (whole-word match).
  • awk '{print $2}' — extracts the interface name.
  • head -n1 — defensive; keeps the first one.

That name goes to K3s as --flannel-iface: the interface over which the Pod network (flannel) talks between nodes.

4. Server flags — what each one is for

With IFACE resolved, the server is installed like this (real snippet from the repo):

curl -sfL https://get.k3s.io | K3S_TOKEN="${TOKEN}" INSTALL_K3S_EXEC="server \
  --node-ip=${SERVER_IP} \
  --advertise-address=${SERVER_IP} \
  --flannel-iface=${IFACE} \
  --tls-san=${SERVER_IP} \
  --write-kubeconfig-mode=644" sh -
FlagWhat it doesWithout it…
--node-ipIP the kubelet registers as a node.registers with the NAT (10.0.2.x); server and worker live in disjoint worlds and flannel breaks.
--advertise-addressIP the API server advertises for clients to reach.advertises a bad IP; clients cannot connect.
--flannel-ifaceinterface of the Pod network (CNI/flannel).points at the NAT; the nodes cannot see each other.
--tls-sanextra IP in the API server certificate.the worker fails to validate the cert (x509 … no IP SANs).
--write-kubeconfig-mode=644readable kubeconfig for every user.vagrant cannot read /etc/rancher/k3s/k3s.yaml without sudo.

server.sh also appends export KUBECONFIG=/etc/rancher/k3s/k3s.yaml to the user's .bashrc: kubectl works without sudo or extra flags. No --bind-address is needed: by default the API server also listens on 127.0.0.1, so the server's local kubectl works.

5. The worker — only one new concept

On the worker there is only one new idea: K3S_URL.

curl -sfL https://get.k3s.io | \
  K3S_URL="https://192.168.56.110:6443" \
  K3S_TOKEN="${TOKEN}" \
  INSTALL_K3S_EXEC="agent \
    --node-ip=192.168.56.111 \
    --flannel-iface=${IFACE}" sh -

K3S_URL tells the installer to create the k3s-agent service (not k3s), and K3S_TOKEN uses the pinned token instead of generating another. The agent is a simple client: it connects to the URL, validates the server's certificate and registers with --node-ip. No --advertise-address, no --tls-san.

Predictions and exercises

Exercise 2.1 — The cluster token

You are alone with the Vagrantfile and the scripts. How does <login>SW get the token without copying node-token? Which problem does that choice remove?

Show answer

Option A (sync): wait for the server to write /var/lib/rancher/k3s/server/node-token and copy it (scp/SSH). Problems: boot-order dependent, and the shared folder is disabled.

Option B (fixed token): define the token in the Vagrantfile and pass it to both scripts via args. The installer honors K3S_TOKEN and does not generate one. No copies, no ordering.

Exercise 2.2 — The network interface

Why not write --flannel-iface=eth1 directly in both scripts?

Show answer

The private NIC name is chosen by the provider: libvirt calls it eth1, VirtualBox enp0s8… Hardcoding it works on only one machine. We fix the private IP ourselves, so the interface is resolved with the pipeline ip -o -4 addr show | grep -w "$IP" | awk '{print $2}' — the same code works on both providers.

Exercise 2.4 — Diagnosing a "worker NotReady"

vagrant up finished, but kubectl get nodes shows only <login>S Ready; <login>SW is NotReady. Order of suspects, most likely first:

#SuspectWhat confirms (or rules out) itCommand
1Flannel / interfaceThe worker registered a NAT IP (10.0.2.x) instead of 192.168.56.111.kubectl get nodes -o wide · journalctl -u k3s-agent -n 50 · ip -o -4 addr show
2TokenThe agent cannot authenticate (HTTP 401).journalctl -u k3s-agent | grep -i token

Mental order

flannel → token → certificate → firewall. kubectl get nodes -o wide tells "wrong IP" from "healthy node" in one second.

Frequent mistakes
  • Thinking the agent "asks" the server for the token at runtime → it is passed via the K3S_TOKEN env in the provisioners, pinned in the Vagrantfile.
  • Hardcoding the private NIC in the scripts → breaks on another provider.
  • Confusing --node-ip (which IP the node registers as) with --advertise-address (which IP the API server announces).
  • Thinking --tls-san is a client-side option; it actually fills the API server's certificate SANs that the agent (and remote kubectl) validate.
  • Diagnosing the worker by reading the server: the answer lives in the worker's own journalctl -u k3s-agent.
