Clase 4 · K3d, Argo CD y GitOps con p3Class 4 · K3d, Argo CD and GitOps with p3

K3s · K3d · Argo CD · GitOps · Application CRD
Objetivo

Entender cómo se despliega una aplicación desde GitHub sin tocar el cluster: K3d vs K3s, los namespaces argocd y dev, la Application CRD de Argo CD (repoURL, targetRevision, path, destination), el sync automático con prune y selfHeal, por qué el install de Argo CD necesita --server-side, y sobre todo por qué cambiar deployment.yaml solo en local no basta.

1. La topología de p3 — ficheros

srcs/p3/
├── scripts/
│   └── install.sh            ← único script: cluster + Argo CD + Application
└── confs/
    ├── application.yaml      ← la "orden" de Argo CD (se aplica al cluster)
    └── manifests/            ← la app que Argo CD vigila (vive en GitHub)
        ├── deployment.yaml   (wil42/playground:v1 o v2)
        └── service.yaml
Los roles de cada fichero
FicheroRol
scripts/install.shPreflight Docker, instala kubectl/k3d/argocd en ~/.local/bin, recrea el cluster iot, crea namespaces, instala Argo CD y aplica la Application.
confs/application.yamlCRD Application: le dice a Argo CD qué repo vigilar, qué path y en qué namespace desplegar.
confs/manifests/deployment.yamlManifiesto de la app (con image: wil42/playground:v1) — la fuente de verdad de Argo CD.
confs/manifests/service.yamlService ClusterIP que expone el puerto 8888 dentro del cluster.

La diferencia de arquitectura frente a p1 y p2

p1/p2:  Vagrant + VM(generic/ubuntu2204) + K3s dentro de la VM
p3:     Docker + K3d (K3s dentro de un contenedor) + Argo CD + un repo GitHub

Nada de esto corre en una VM: install.sh se ejecuta en el host. No hace falta sudo porque las herramientas se instalan en ~/.local/bin; el único requisito previo es Docker arrancado y accesible (docker info).

2. K3s vs K3d — la pregunta que el subject obliga a saber

Clave

K3d no es "otra Kubernetes": es K3s empaquetado en contenedores Docker. El cluster que ves con kubectl get nodes es el mismo K3s que en p1/p2, pero sin VM: lo que el subject pide es que sepas cuándo usar cada uno.

3. El flujo completo de p3

  GitHub (repo público, manifiestos en srcs/p3/confs/manifests, tag v1/v2)
                  │
     Argo CD pollea el repo cada ~3 min  (sync automático)  ── o sync manual
                  ▼
   Argo CD (namespace argocd)
     └─ Application CRD "playground"  ──sync──►  aplica manifests al cluster
                  ▼
   K3d cluster "iot" · namespace dev
     ├─ Deployment playground  (wil42/playground:v1|v2)
     └─ Service    playground  (ClusterIP, 8888)
                  ▲
      kubectl -n dev port-forward svc/playground 8888:8888

El punto clave de GitOps: nadie aplica manifiestos a mano. El cluster se "declara en Git" y Argo CD se encarga de que la realidad coincida con esa declaración.

4. install.sh sección a sección

4.1 Preflight — Docker obligatorio

[ -x docker ] || exit                      # ¿está instalado?
docker info   || exit                      # ¿el daemon responde?

K3d no funciona sin Docker: cada nodo del cluster es un contenedor. Los errores de permisos se arreglan con sudo usermod -aG docker $USER y volver a iniciar sesión.

4.2 Tooling sin sudo en ~/.local/bin

kubectl  ← descargado   de dl.k8s.io (versión stable)
k3d      ← instalador oficial de k3d
argocd   ← CLI binario de argo-cd releases (solo útil para sync/login opcional)
export PATH="${BIN}:${PATH}"

Nada necesita paquetes del sistema: todo termina en HOME/.local/bin, así el evaluador solo necesita Docker.

4.3 El cluster, desde cero

k3d cluster delete iot  >/dev/null 2>&1 || true
k3d cluster create iot  --wait

Cada ejecución borra y recrea el cluster (estado conocido, reproducible). --wait espera a que el cluster esté listo antes de seguir.

4.4 Namespaces

kubectl create namespace argocd --dry-run=client -o yaml | kubectl apply -f -
kubectl create namespace dev    --dry-run=client -o yaml | kubectl apply -f -
  • argocd → el controlador (componentes de Argo CD).
  • dev → la aplicación (donde aterrizan los manifiestos de GitHub).
  • El --dry-run=client -o yaml | apply -f - convierte el comando en idempotente: se puede repetir sin error.

4.5 Argo CD, instalar con --server-side

kubectl apply --server-side -n argocd \
  -f https://raw.githubusercontent.com/argoproj/argo-cd/stable/manifests/install.yaml
kubectl -n argocd rollout status deploy/argocd-repo-server --timeout=300s
kubectl -n argocd rollout status deploy/argocd-server      --timeout=300s
  • El install.yaml es el manifiesto oficial: instala todos los componentes Argo CD en el namespace argocd.
  • Por qué --server-side: kubectl apply normal anota cada objeto con la configuración aplicada (last-applied-configuration), y esa anotación tiene un límite de 262144 bytes. Los CRDs de Argo CD (los tipos Application y AppProject) superan ese tamaño en metadatos; con --server-side el servidor gestiona la reconciliación en el propio modelo de Kubernetes y se evita el límite.
  • Las dos esperas son los componentes que importan para el sync del repo: argocd-repo-server (lee el Git) y argocd-server (API + UI).

4.6 La Application — el corazón GitOps

kubectl apply -f "${CONFS}/application.yaml"

Esto no es un manifiesto de la app: le dice a Argo CD qué repo vigilar, en qué path y hacia dónde sincronizar. A partir de aquí es el propio controller quien despliega.

4.7 Esperar el primer sync

for _ in $(seq 1 60); do
  SYNC="$(kubectl -n argocd get application playground -o jsonpath='{.status.sync.status}' ...)"
  HEALTH="$(kubectl -n argocd get application playground -o jsonpath='{.status.health.status}' ...)"
  [ "${SYNC}" = "Synced" ] && [ "${HEALTH}" = "Healthy" ] && break
  sleep 5
done

Lee el status de la Application hasta que queda Synced y Healthy — la señal de que Argo CD ya aplicó los manifests desde GitHub.

4.8 Info final

  • Imprime el password de admin (argocd-initial-admin-secret, en base64).
  • Recuerda los dos port-forwards: UI (8080:443) y app (8888:8888).
  • Avisa si ~/.local/bin no está en el PATH.

5. La Application CRD, campo a campo

confs/application.yaml no se lee desde Git (aunque vive en el repo): se aplica una vez al cluster y es la declaración de intenciones de Argo CD.

apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: playground
  namespace: argocd        # el controller vive aquí
spec:
  project: default         # qué AppProject (política) la gestiona
  source:                  # ← DE DÓNDE mirar
    repoURL: https://github.com//Inception-of-Things_.git
    targetRevision: HEAD   # rama/commit a seguir (HEAD = default)
    path: srcs/p3/confs/manifests
  destination:             # ← DÓNDE aplicar
    server: https://kubernetes.default.svc   # el propio cluster
    namespace: dev
  syncPolicy:              # ← CUÁNDO y CÓMO sync
    automated:
      prune: true          # borra del cluster lo que borras en Git
      selfHeal: true       # revierte cambios hechos a mano en el cluster
    syncOptions:
      - CreateNamespace=true   # crea el ns destino si no existe
CampoQué decideAnalogía
source.repoURLQué repo Git vigila Argo CD"de dónde saco la receta"
source.pathQué subcarpeta del repo usa"qué receta de este libro"
source.targetRevisionQué rama/commit — HEAD"sigue la última versión"
destination.namespaceDónde crea los objetos"en qué cocina la aplico"
destination.serverQué cluster — el suyo (kubernetes.default.svc)"en esta cocina"
automated.prune¿Borrar lo que ya no está en Git?"retira lo que sobra"
automated.selfHeal¿Deshacer ediciones manuales?"la receta manda por encima de mis manos"
Alcance del subject

La práctica del subject de p3 pide solo esto: dos namespaces, una app en dev desplegada por Argo CD desde GitHub, y que cambiar el tag de la imagen en Git basta para desplegar.

6. Continuous deployment — v1 → v2

  1. El deployment.yaml existe en dos sitios: en el repo (GitHub) y en el cluster (copiado por Argo CD). Git es la fuente de verdad, la copia del cluster es un reflejo.
  2. Cambias el tag en tu repo y haces push: 
    sed -i 's|playground:v1|playground:v2|' srcs/p3/confs/manifests/deployment.yaml
git add + commit + push
  3. Argo CD pollea el repo cada ~3 minutos y ve el cambio → aplica → crea un Deployment con la imagen v2 (rollout: el pod viejo va saliendo, entra el nuevo).
  4. Si no quieres esperar al poll, ordenas un sync manual: 
    kubectl -n argocd patch application playground --type merge \
  -p '{"operation":{"sync":{"revision":"HEAD"}}}'
  5. Compruebas el resultado: 
    curl http://localhost:8888/
# {"status":"ok", "message": "v2"}
Por qué "cambiar solo en local no basta"

El deployment.yaml local es un borrador; Argo CD solo lee el remoto. Mientras el commit no se suba, el repo que vigila Argo CD no cambia y no hay nada que sincronizar. GitOps = el cluster converge hacia lo que hay en el repo remoto, no hacia tu disco.

Predicciones y ejercicios

Ejercicio 4.1 — La práctica oficial del plan

¿Por qué cambiar deployment.yaml solo en local no despliega nada, y por qué Argo CD necesita leer el cambio del remoto?

Mostrar solución

Porque Argo CD no mira tu disco: su Application apunta a un repoURL concreto y sincroniza contra el estado de ese repo. Tu deployment.yaml local es solo la fuente para hacer un commit. Hasta que el commit no viaja al remoto (git push), el contenido que Argo CD compara sigue igual → no ve ningún cambio → no sync. Y aunque lo viera, solo aplica manifiestos que vienen del path indicado en el repo, no ficheros locales.

git add + commit                  # prepara el borrador
git push                          #  ← aquí el cambio entra en la fuente de verdad
kubectl get application -n argocd # Synced vs OutOfSync

Ejercicio 4.2 — Por qué --server-side

¿Por qué kubectl apply normal podría fallar al instalar Argo CD, y qué hace --server-side?

Mostrar solución

kubectl apply clásico guarda la configuración aplicada en la anotación kubectl.kubernetes.io/last-applied-configuration, limitada a 262144 bytes. Los CRDs de Argo CD (Application, AppProject) tienen esquemas enormes que superan ese límite → aplicar falla. Con --server-side el API server asume la reconciliación (campo managedFields) y el límite de la anotación deja de importar.

Ejercicio 4.3 — La Application no se lee de Git

¿La application.yaml de p3 la aplica Argo CD? Justifica.

Mostrar solución

No. Es el cliente quien la aplica (kubectl apply -f confs/application.yaml, paso 4.6 del script). Es un objeto CRD Application que configura a Argo CD: le dice qué repo y path vigilar y hacia qué namespace. Argo CD ejecuta lo que ese objeto indica, pero no puede verse a sí mismo leyéndolo de Git — sin la Application aplicada, Argo CD está instalado pero no sabe qué desplegar.

Ejercicio 4.4 — selfHeal en acción

Un evaluador ejecuta kubectl -n dev scale deploy playground --replicas=5 y espera 5 pods. ¿Qué pasa realmente?

Mostrar solución

La Application tiene automated.selfHeal: true, así que Argo CD considera el estado del cluster como "deriva" frente a Git (donde replicas: 1) y lo revierte en el siguiente ciclo (≤3 min por el poll). Puede que veas brevemente 5 pods y luego vuelvan a 1. La prueba es que Git manda: la edición manual no sobrevive. (La misma lógica protegería borrar el Deployment: prune/selfHeal lo restauran.)

Ejercicio 4.5 — La pregunta girada de defensa

"Después de un git push la app nunca cambia de versión. ¿Qué compruebas?"

Mostrar solución
  1. Que el push fue al repo correcto (git remote -v) y la rama coincide con targetRevision (HEAD → la rama por defecto).
  2. Estado de la Application: kubectl get application playground -n argocd ↔ OutOfSync/ComparisonError.
  3. Si está OutOfSync, Argo CD aún no ha hecho el poll → sync manual con el patch --operation. Si ComparisonError, revisar repoURL, path y credenciales.
  4. Si Synced pero la imagen vieja, ver el rollout: kubectl -n dev rollout status deploy/playground y el tag: kubectl get deploy playground -n dev -o jsonpath='{.spec.template.spec.containers[0].image}'.

Ejercicio 4.6 — Namespaces y destino

¿Qué pasaría si destination.namespace: dev no existiera y la Application no tuviera CreateNamespace=true?

Mostrar solución

La sincronización fallaría: Argo CD no puede crear un Deployment en un namespace que no existe. Por eso el script crea dev explícitamente y la Application añade syncOptions: [CreateNamespace=true] — doble garantía. El error aparecería en status.operationState.message tipo namespaces "dev" not found.

Errores frecuentes
  • Confundir application.yaml con un manifiesto de la app: es la configuración de Argo CD, se aplica al cluster.
  • Creer que editar el deployment.yaml local ya despliega → no, falta git push (y el poll de Argo CD).
  • Escribir repoURL/path mal → ComparisonError. El path es relativo a la raíz del repo: srcs/p3/confs/manifests.
  • Aplicar los manifests de la app a mano con kubectl apply y luego "no entender por qué se revierten" → es selfHeal, el cluster manda a Git.
  • Instalar Argo CD con kubectl apply normal → falla por el límite de las anotaciones; se necesita --server-side.
  • Olvidar el port-forward: el Service es ClusterIP, no hay IP pública de la app en p3 — se accede con port-forward.
  • Tratar de usar el cluster de p1/p2: p3 es un cluster K3d distinto; los contextos de kubectl son diferentes.
  • No saber distinguir K3s de K3d (pregunta expresa del subject).

4. install.sh section by section

4.1 Preflight — Docker required

[ -x docker ] || exit                      # is it installed?
docker info   || exit                      # does the daemon respond?

K3d does not work without Docker: every cluster node is a container. Permission errors are fixed with sudo usermod -aG docker $USER and re-login.

4.2 Tooling without sudo in ~/.local/bin

kubectl  ← downloaded from dl.k8s.io (stable version)
k3d      ← official k3d installer
argocd   ← argo-cd releases binary CLI (only for optional sync/login)

No system packages needed: everything ends up in HOME/.local/bin, so the evaluator only needs Docker.

4.3 The cluster, from scratch

k3d cluster delete iot  >/dev/null 2>&1 || true
k3d cluster create iot  --wait

Every run deletes and recreates the cluster (known, reproducible state). --wait blocks until the cluster is ready.

4.4 Namespaces

kubectl create namespace argocd --dry-run=client -o yaml | kubectl apply -f -
kubectl create namespace dev    --dry-run=client -o yaml | kubectl apply -f -
  • argocd → the controller (Argo CD components).
  • dev → the application (where the GitHub manifests land).
  • The --dry-run=client -o yaml | apply -f - trick makes the command idempotent: safe to repeat.

4.5 Argo CD, installed with --server-side

kubectl apply --server-side -n argocd \
  -f https://raw.githubusercontent.com/argoproj/argo-cd/stable/manifests/install.yaml
kubectl -n argocd rollout status deploy/argocd-repo-server --timeout=300s
kubectl -n argocd rollout status deploy/argocd-server      --timeout=300s
  • install.yaml is the official manifest: it installs all Argo CD components in the argocd namespace.
  • Why --server-side: plain kubectl apply annotates every object with the applied config (last-applied-configuration), and that annotation has a 262144-byte limit. Argo CD's CRDs (the Application and AppProject types) exceed that size in metadata; with --server-side the API server owns the reconciliation (the managedFields field) and the annotation limit stops mattering.
  • The two waits are the components that matter for repo sync: argocd-repo-server (reads Git) and argocd-server (API + UI).

4.6 The Application — the GitOps heart

kubectl apply -f "${CONFS}/application.yaml"

This is not an app manifest: it tells Argo CD which repo to watch, at which path, and where to sync to. From here on the controller itself deploys.

4.7 Waiting for the first sync

for _ in $(seq 1 60); do

It reads the Application status until it becomes Synced and Healthy — the signal that Argo CD has already applied the manifests from GitHub.

5. The Application CRD, field by field

confs/application.yaml is not read from Git (even though it lives in the repo): it is applied once to the cluster and is Argo CD's statement of intent.

apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: playground
  namespace: argocd        # the controller lives here
spec:
  project: default         # which AppProject (policy) manages it
  source:                  # ← WHERE TO LOOK
    repoURL: https://github.com//Inception-of-Things_.git
    targetRevision: HEAD   # branch/commit to follow (HEAD = default)
    path: srcs/p3/confs/manifests
  destination:             # ← WHERE TO APPLY
    server: https://kubernetes.default.svc   # the cluster itself
    namespace: dev
  syncPolicy:              # ← WHEN and HOW to sync
    automated:
      prune: true          # delete from the cluster what you delete in Git
      selfHeal: true       # revert manual changes to the cluster
    syncOptions:
      - CreateNamespace=true   # create the target ns if it does not exist
FieldWhat it decidesAnalogy
source.repoURLWhich Git repo Argo CD watches"where I get the recipe"
source.pathWhich subfolder of the repo it uses"which recipe in this book"
source.targetRevisionWhich branch/commit — HEAD"follow the latest version"
destination.namespaceWhere it creates the objects"in which kitchen I apply it"
destination.serverWhich cluster — its own (kubernetes.default.svc)"in this kitchen"
automated.pruneDelete what is no longer in Git?"clear away what is extra"
automated.selfHealUndo manual edits?"the recipe outranks my hands"
Subject scope

The p3 practice asks for only this: two namespaces, one app in dev deployed by Argo CD from GitHub, and changing the image tag in Git being enough to deploy.

6. Continuous deployment — v1 → v2

  1. deployment.yaml exists in two places: in the repo (GitHub) and in the cluster (copied by Argo CD). Git is the source of truth; the cluster copy is a reflection.
  2. You change the tag in your repo and push: 
    sed -i 's|playground:v1|playground:v2|' srcs/p3/confs/manifests/deployment.yaml
git add + commit + push
  3. Argo CD polls the repo every ~3 minutes, sees the change → applies → creates a Deployment with the v2 image (rollout: the old pod exits, the new one enters).
  4. If you do not want to wait for the poll, you order a manual sync: 
    kubectl -n argocd patch application playground --type merge \
  -p '{"operation":{"sync":{"revision":"HEAD"}}}'
  5. You check the result: 
    curl http://localhost:8888/
# {"status":"ok", "message": "v2"}
Why "changing locally alone is not enough"

The local deployment.yaml is a draft; Argo CD only reads the remote. Until the commit is pushed, the repo Argo CD watches has not changed and there is nothing to sync. GitOps = the cluster converges toward the remote repo, not your disk.

Predictions and exercises

Exercise 4.1 — The official practice of the plan

Why does changing deployment.yaml only locally deploy nothing, and why does Argo CD need to read the change from the remote?

Show answer

Because Argo CD does not look at your disk: its Application points at a specific repoURL and syncs against that repo's state. Your local deployment.yaml is only the source for a commit. Until the commit travels to the remote (git push), the content Argo CD compares stays the same → it sees no change → no sync. And even if it saw it, it only applies manifests coming from the path in the repo, not local files.

git add + commit                  # prepare the draft
git push                          #  ← here the change enters the source of truth
kubectl get application -n argocd # Synced vs OutOfSync

Exercise 4.2 — Why --server-side

Why could a normal kubectl apply fail when installing Argo CD, and what does --server-side do?

Show answer

Classic kubectl apply stores the applied configuration in the kubectl.kubernetes.io/last-applied-configuration annotation, capped at 262144 bytes. Argo CD's CRDs (Application, AppProject) have huge schemas that overflow that limit → apply fails. With --server-side the API server takes over reconciliation (the managedFields field) and the annotation limit stops mattering.

Exercise 4.3 — The Application is not read from Git

Is p3's application.yaml applied by Argo CD? Justify.

Show answer

No. The client applies it (kubectl apply -f confs/application.yaml, step 4.6 of the script). It is an Application CRD that configures Argo CD: it tells it which repo and path to watch and toward which namespace. Argo CD executes what that object says, but it cannot read itself from Git — without the Application applied, Argo CD is installed but does not know what to deploy.

Exercise 4.4 — selfHeal in action

An evaluator runs kubectl -n dev scale deploy playground --replicas=5 and expects 5 pods. What actually happens?

Show answer

The Application has automated.selfHeal: true, so Argo CD treats the cluster state as "drift" against Git (where replicas: 1) and reverts it on the next cycle (≤3 min via poll). You may briefly see 5 pods and then back to 1. The proof is that Git wins: the manual edit does not survive. (The same logic would protect against deleting the Deployment: prune/selfHeal restore it.)

Exercise 4.5 — The flipped defense question

"After a git push the app never changes version. What do you check?"

Show answer
  1. That the push went to the right repo (git remote -v) and the branch matches targetRevision (HEAD → the default branch).
  2. Application status: kubectl get application playground -n argocd ↔ OutOfSync/ComparisonError.
  3. If OutOfSync, Argo CD has not polled yet → manual sync with the patch --operation. If ComparisonError, review repoURL, path and credentials.
  4. If Synced but the old image, check the rollout: kubectl -n dev rollout status deploy/playground and the tag: kubectl get deploy playground -n dev -o jsonpath='{.spec.template.spec.containers[0].image}'.

Exercise 4.6 — Namespaces and destination

What would happen if destination.namespace: dev did not exist and the Application had no CreateNamespace=true?

Show answer

The sync would fail: Argo CD cannot create a Deployment in a namespace that does not exist. That is why the script creates dev explicitly and the Application adds syncOptions: [CreateNamespace=true] — double guarantee. The error would appear in status.operationState.message as namespaces "dev" not found.

Frequent mistakes
  • Confusing application.yaml with an app manifest: it is Argo CD's configuration, applied to the cluster.
  • Believing editing the local deployment.yaml already deploys → no, it needs git push (and Argo CD's poll).
  • Wrong repoURL/path → ComparisonError. The path is relative to the repo root: srcs/p3/confs/manifests.
  • Applying the app manifests by hand with kubectl apply and then "not understanding why they get reverted" → it is selfHeal, the cluster follows Git.
  • Installing Argo CD with plain kubectl apply → fails because of the annotation limit; --server-side is required.
  • Forgetting the port-forward: the Service is ClusterIP, the app has no public IP in p3 — you access it via port-forward.
  • Trying to reuse the p1/p2 cluster: p3 is a different K3d cluster; the kubectl contexts differ.
  • Not being able to tell K3s from K3d (an explicit subject question).
