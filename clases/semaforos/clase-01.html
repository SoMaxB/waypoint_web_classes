Clase 1 · procesos, hilos, carrera y sección críticaClass 1 · processes, threads, races and critical sections

C · POSIX · pthreads
Objetivo

Construir el modelo mental mínimo de la concurrencia en C: qué es un hilo, qué significa que dos hilos compartan memoria, por qué una operación como i++ no es atómica y cómo una condición de carrera produce resultados erróneos. Al terminar debes poder dibujar el interleaving de dos hilos sobre una variable compartida y señalar el punto exacto donde se pierde la exclusión.

1. Procesos frente a hilos

Un proceso es una instancia de un programa en ejecución. Cada proceso tiene su propia memoria, sus propios descriptores y su propio espacio de direcciones. Dos procesos no ven la memoria del otro sin un mecanismo explícito.

Un hilo (thread) es una línea de ejecución dentro de un proceso. Todos los hilos de un mismo proceso comparten la misma memoria, los mismos descriptores y el mismo espacio de direcciones. Esa memoria compartida es la fuente de los problemas que veremos.

Proceso A                  Proceso B
+------------------------+  +------------------------+
| memoria propia         |  | memoria propia          |
| hilo a1, hilo a2       |  | hilo b1                 |
+------------------------+  +------------------------+

Proceso C (un solo proceso con varios hilos)
+----------------------------------------+
| memoria ÚNICA                          |
| hilo c1  hilo c2  hilo c3  (comparten) |
+----------------------------------------+

Modelo mental: un hilo es lo que la CPU ejecuta; un proceso es la "caja" que le da memoria. Varios hilos comparten la caja.

2. El programador y el interleaving

El kernel tiene un planificador (scheduler) que interrumpe un hilo y ejecuta otro. El orden en que se entrelazan las instrucciones se llama interleaving y no es determinista: no podemos predecir cuál se ejecutará primero ni en qué punto.

hilo c1:   A   B   C
hilo c2:      X     Y

Interleaving posible: A X B C Y
Otro posible:          X A Y B C

Dos hilos pueden intercalarse dentro de una misma operación si esa operación usa varias instrucciones.

3. Operaciones atómicas y no atómicas

Una operación es atómica si, desde fuera del hilo que la ejecuta, parece indivisible: no hay un punto intermedio observable. En C, la mayoría de las operaciones de alto nivel no son atómicas.

Por ejemplo, counter++ en C se traduce en varias instrucciones de máquina:

1. leer   el valor de counter desde memoria   (load)
2. sumar  1 al valor leído                    (add)
3. escribir el resultado de vuelta a memoria  (store)

Hay un punto observable entre la lectura y la escritura: otro hilo puede ver counter con el valor antiguo o con el nuevo, pero no "a medias del incremento". El problema es que dos hilos pueden intercalarse entre esos tres pasos.

4. Condición de carrera

Una condición de carrera ocurre cuando el resultado depende del orden en que se ejecutan los hilos. Es un error: el resultado puede ser distinto en cada ejecución del mismo programa.

Ejemplo con dos hilos que ambos ejecutan counter++ partiendo de counter = 0:

#include <stdio.h>
#include <pthread.h>

static int counter = 0;

void *inc(void *arg) {
    (void)arg;
    for (int i = 0; i < 100000; i++) counter++;
    return NULL;
}

int main(void) {
    pthread_t t1, t2;
    pthread_create(&t1, NULL, inc, NULL);
    pthread_create(&t2, NULL, inc, NULL);
    pthread_join(t1, NULL);
    pthread_join(t2, NULL);
    printf("counter = %d\n", counter);   /* ¿200000? */
    return 0;
}

Intuitivamente querríamos 200000, pero a menudo es menor. El interleaving "pierde" incrementos:

hilo c1:   leer 0  -> sumar -> 1 -> escribir 1
hilo c2:     leer 0 (ve el valor ANTES del store de c1)
             -> sumar -> 1 -> escribir 1

Resultado: 1 en lugar de 2. Se perdió un incremento.

Ambos hilos leyeron 0; ambos escribieron 1. El segundo store pisa al primero. Esa es la condición de carrera: el resultado depende del interleaving.

5. Sección crítica

Una sección crítica es el fragmento de código que accede a un recurso compartido y que no debe ejecutarse a la vez que otra sección crítica sobre el mismo recurso.

En el ejemplo anterior, el cuerpo counter++ es la sección crítica. El objetivo de la sincronización es garantizar una propiedad llamada exclusión mutua: si un hilo está en la sección crítica, ningún otro puede entrar hasta que salga.

Necesitamos una herramienta que:

  • Impida que dos hilos estén simultáneamente dentro de la sección crítica.
  • No dependa de adivinar el interleaving.
  • Funcione agente casual: dé resultados reproducibles.

Esa herramienta, en este concepto, es el semáforo (clase 2). Existe otra, el mutex, que veremos a fondo en POSIX Threads.

6. Cuándo hace falta sincronización

Se necesita cuando se cumplen las tres condiciones a la vez:

  1. Hay un recurso compartido entre varios hilos (una variable global, un buffer, un descriptor).
  2. Hay al menos una escritura sobre ese recurso.
  3. Los hilos no se coordinan de otro modo.

Si el recurso es de solo lectura, no hace falta. Si cada hilo tuviera su propia copia, tampoco. El "riesgo" empieza cuando se comparte algo que se escribe.

7. Predicciones y ejercicios

Desarrolla cada uno antes de mirar la solución.

Predicción 1 · interleaving de i++

Dos hilos ejecutan i++ con i = 0 inicial. Escribe una secuencia de interleaving concreta que termine en i = 1 explicando qué instrucción del hilo B ve un valor ya desactualizado.

Mostrar solución 
A: load i  (lee 0)
B: load i  (lee 0, A aún no ha escrito)
A: add  -> 1 ; store -> i = 1
B: add  -> 1 ; store -> i = 1  (pisa el store de A)
Resultado: i = 1
Predicción 2 · qué es atómico

Di si las siguientes operaciones son atómicas a nivel de máquina y por qué:

  1. x = 5; (guardar una constante en una variable int).
  2. counter += 1;
  3. str++; (avanzar un puntero).
Mostrar solución

1. Normalmente sí: un store de un int alineado suele ser atómico en x86-64.

2. No: implica load, add, store.

3. No: es load del puntero + add + store del nuevo valor. Aunque el "avance" sea de una unidad, son varias instrucciones.

La atomicidad depende de la plataforma y de si hay un punto observable a mitad de camino; el estándar no promete nada sobre instrucciones concretas, solo sobre primitivas como los atómicos de C11.

Predicción 3 · ¿siempre hay carrera?

Tres hilos incrementan cada uno 1000 veces una variable compartida. ¿El resultado está garantizado? Justifica.

Mostrar solución

No. El resultado puede ser menor que 3000 dependiendo del interleaving. La presencia de la carrera no garantiza un valor erróneo en cada ejecución: puede "acertar" por casualidad. Que no salte cada vez no significa que el código sea correcto.

Ejercicio · localizar la sección crítica

Dada esta función que dos hilos llaman sobre la misma estructura struct msg *m:

void add(struct msg *m, int n) {
    m->total += n;
    m->count++;
}

Localiza la sección crítica, la escritura compartida y explica qué resultado querríamos y cuál puede pasar.

Mostrar solución
  • Recurso compartido: m->total y m->count (ambos se leen y escriben).
  • Sección crítica: ambas sentencias del cuerpo de add, pues tocan el mismo recurso.
  • Resultado esperado: si dos hilos llaman add(m, 1) y add(m, 2), querríamos total incrementado en 3 y count en 2.
  • Resultado posible: si los hilos intercalan dentro de m->total += n, se pierde una suma; y el par total/count puede quedar incoherente de forma transitoria. De aquí surge también la idea de que a veces hace falta proteger más de una variable a la vez.
Errores frecuentes
  • Pensar que "escribo código simple, así que no hace falta sincronización". La necesidad no depende de la complejidad sino de compartir una escritura.
  • Creer que i++ es atómico porque en el lenguaje parece una sola operación.
  • Asumir que el resultado erróneo aparece siempre; una carrera puede pasar desapercibida en pruebas.
  • Confundir hilos con procesos y asumir que no comparten memoria.
  • Intentar "arreglar" la carrera durmiendo hilos o esperando con usleep; eso cambia la probabilidad, no elimina el problema.
  • Creer que leer y escribir la misma variable desde un único hilo es un problema; la carrera exige al menos dos.

Has aprendido que

  • Un hilo comparte la memoria de su proceso con sus hermanos; un proceso no.
  • El orden de ejecución de los hilos (interleaving) lo decide el planificador y no es determinista.
  • Una operación en C no es atómica por defecto; i++ son varias instrucciones.
  • Un interleaving entre load, add y store puede perder incrementos.
  • Una condición de carrera es un resultado que depende del orden de ejecución.
  • Una sección crítica toca un recurso compartido y debe correr con exclusión mutua.
  • La sincronización es necesaria cuando se comparte un recurso que se escribe.
  • Dormir hilos o esperar no arregla una carrera; solo cambia su probabilidad.

Objective

Build the minimum mental model of concurrency in C: what a thread is, what it means for two threads to share memory, why an operation like i++ is not atomic, and how a race condition produces wrong results. By the end you must be able to draw the interleaving of two threads over a shared variable and point out the exact spot where mutual exclusion is lost.

1. Processes vs threads

A process is an instance of a running program. Each process has its own memory, its own file descriptors and its own address space. Two processes cannot see each other's memory without an explicit mechanism.

A thread is a line of execution inside a process. All threads of the same process share the same memory, the same descriptors and the same address space. That shared memory is the source of the problems we will look at.

Process A                  Process B
+------------------------+  +------------------------+
| own memory             |  | own memory             |
| thread a1, thread a2   |  | thread b1              |
+------------------------+  +------------------------+

Process C (one process with several threads)
+----------------------------------------+
| SHARED memory                          |
| thread c1  thread c2  thread c3        |
+----------------------------------------+

Mental model: a thread is what the CPU executes; a process is the "box" that gives it memory. Several threads share the box.

2. The scheduler and interleaving

The kernel has a scheduler that interrupts one thread and runs another. The order in which instructions interleave is called interleaving and is not deterministic: we cannot predict which one runs first or at which point.

thread c1:   A   B   C
thread c2:      X     Y

Possible interleaving: A X B C Y
Another one:           X A Y B C

Two threads can interleave inside a single operation if that operation uses several instructions.

3. Atomic and non-atomic operations

An operation is atomic if, seen from outside the thread running it, it looks indivisible: there is no observable middle point. In C, most high-level operations are not atomic.

For example, counter++ compiles to several machine instructions:

1. load   the value of counter from memory   (load)
2. add    1 to the value read                 (add)
3. store  the result back to memory           (store)

There is an observable point between the read and the write: another thread can see counter with its old value or its new value, but never "half of the increment". The problem is that two threads can interleave between those three steps.

4. Race condition

A race condition happens when the result depends on the order in which threads run. It is a bug: the result can differ on every run of the same program.

Example with two threads both running counter++ starting from counter = 0:

#include <stdio.h>
#include <pthread.h>

static int counter = 0;

void *inc(void *arg) {
    (void)arg;
    for (int i = 0; i < 100000; i++) counter++;
    return NULL;
}

int main(void) {
    pthread_t t1, t2;
    pthread_create(&t1, NULL, inc, NULL);
    pthread_create(&t2, NULL, inc, NULL);
    pthread_join(t1, NULL);
    pthread_join(t2, NULL);
    printf("counter = %d\n", counter);   /* 200000? */
    return 0;
}

Intuitively we would expect 200000, but it is often smaller. The interleaving "loses" increments:

thread c1:   load 0  -> add -> 1 -> store 1
thread c2:     load 0 (sees the value BEFORE c1's store)
               -> add -> 1 -> store 1

Result: 1 instead of 2. One increment was lost.

Both threads read 0; both wrote 1. The second store overwrites the first. That is the race condition: the result depends on the interleaving.

5. Critical section

A critical section is the piece of code that accesses a shared resource and must not run at the same time as another critical section over the same resource.

In the previous example, the body counter++ is the critical section. The goal of synchronization is to guarantee a property called mutual exclusion: if a thread is inside the critical section, no other thread can enter until it leaves.

We need a tool that:

  • Prevents two threads from being simultaneously inside the critical section.
  • Does not depend on guessing the interleaving.
  • Works by accident: gives reproducible results.

That tool, in this concept, is the semaphore (class 2). There is another one, the mutex, which we cover in depth in POSIX Threads.

6. When synchronization is needed

It is needed when the three conditions hold at once:

  1. There is a shared resource between several threads (a global variable, a buffer, a descriptor).
  2. There is at least one write to that resource.
  3. Threads do not coordinate in any other way.

If the resource is read-only, no synchronization is needed. If each thread had its own copy, none either. The "risk" starts when you share something that is written.

Prediction 1 · interleaving of i++

Two threads run i++ starting from i = 0. Write a concrete interleaving that ends in i = 1, explaining which instruction of thread B sees an already stale value.

Show answer 
A: load i  (reads 0)
B: load i  (reads 0, A has not written yet)
A: add  -> 1 ; store -> i = 1
B: add  -> 1 ; store -> i = 1  (overwrites A's store)
Result: i = 1
Prediction 2 · what is atomic

Say whether the following operations are atomic at the machine level and why:

  1. x = 5; (storing a constant into an int variable).
  2. counter += 1;
  3. str++; (advancing a pointer).
Show answer

1. Usually yes: an aligned store of an int is typically atomic on x86-64.

2. No: it involves load, add, store.

3. No: it is a load of the pointer + add + store of its new value. Even though the "advance" is by one unit, those are several instructions.

Atomicity depends on the platform and on whether there is an observable point halfway through; the standard promises nothing about specific instructions, only about primitives like C11 atomics.

Prediction 3 · is there always a race?

Three threads each increment a shared variable 1000 times. Is the result guaranteed? Justify.

Show answer

No. The result can be lower than 3000 depending on the interleaving. A race does not guarantee a wrong value on every run: it can "get lucky". Not crashing every time does not mean the code is correct.

Exercise · locate the critical section

Two threads call this function on the same struct msg *m:

void add(struct msg *m, int n) {
    m->total += n;
    m->count++;
}

Locate the critical section, the shared write, and explain the result we would want and the one that can happen.

Show answer
  • Shared resource: m->total and m->count (both are read and written).
  • Critical section: both statements in the body of add, since they touch the same resource.
  • Expected result: if two threads call add(m, 1) and add(m, 2), we would want total incremented by 3 and count by 2.
  • Possible result: if the threads interleave inside m->total += n, a sum is lost; and the total/count pair can become temporarily incoherent. This also leads to the idea that sometimes more than one variable needs protecting at once.
Common mistakes
  • Thinking "my code is simple, so it needs no synchronization". The need depends on sharing a write, not on code complexity.
  • Believing i++ is atomic because it looks like one operation in the language.
  • Assuming the wrong result always shows up; a race can go unnoticed in tests.
  • Confusing threads with processes and assuming they do not share memory.
  • Trying to "fix" the race by sleeping threads or waiting with usleep; that changes the probability, it does not remove the problem.
  • Thinking that reading and writing the same variable from a single thread is a problem; a race needs at least two.

You have learned that

  • A thread shares its process memory with its siblings; a process does not.
  • The execution order of threads (interleaving) is decided by the scheduler and is not deterministic.
  • An operation in C is not atomic by default; i++ is several instructions.
  • An interleaving between load, add and store can lose increments.
  • A race condition is a result that depends on the order of execution.
  • A critical section touches a shared resource and must run with mutual exclusion.
  • Synchronization is needed when a shared resource is written.
  • Sleeping threads or waiting does not fix a race; it only changes its probability.
