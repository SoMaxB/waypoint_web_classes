Clase 2 · entorno, cargador manual y primer triánguloClass 2 · environment, manual loader and first triangle

OpenGL · GLFW · glfwGetProcAddress · VBO · VAO
Objetivo

Montar el esqueleto real de Scop sobre el que se construirán todas las demás clases: ventana GLFW, contexto OpenGL, cargador manual de las funciones de OpenGL, shaders mínimos, VBO/VAO y bucle de render. Al terminar esta clase debes poder explicar qué aporta GLFW, qué es un contexto OpenGL y por qué debe ser actual, por qué las funciones de OpenGL hay que cargarlas en runtime y no enlazarlas, qué diferencia hay entre declarar, definir y asignar un puntero a función, cómo se conectan los atributos del shader con los datos del buffer y por qué el bucle de render necesita glfwSwapBuffers() y glfwPollEvents().

Esta clase se tomó de forma interactiva y cumple la regla del proyecto: se escribió, compiló con -Wall -Wextra -Werror y ejecutó código real. El resultado observable fue una ventana clara y un triángulo naranja dibujado por nuestro propio pipeline.

1. Qué estamos aislando

Esta clase no carga todavía .obj, no usa matrices MVP y no aplica texturas. Aísla dos preguntas:

1. ¿Qué tiene que existir antes de que el GPU pueda dibujar algo?
2. ¿Cómo se obtienen las funciones de OpenGL que el GPU va a ejecutar?

El flujo mínimo es:

programa
  ↓
inicializar librería de ventana (glfwInit)
  ↓
pedir contexto core 3.3 (glfwWindowHint ANTES de crear ventana)
  ↓
crear ventana + contexto OpenGL (glfwCreateWindow)
  ↓
hacer el contexto actual (glfwMakeContextCurrent)
  ↓
cargar funciones OpenGL (cargador manual, después del contexto)
  ↓
crear shaders y compilarlos
  ↓
crear datos del triángulo y subirlos a VBO/VAO
  ↓
bucle de eventos (glfwWindowShouldClose)
  ↓
dibujar cada frame
  ↓
swap buffers + poll events

La ventana no es la escena. Es el destino donde OpenGL presentará el framebuffer final.

2. Qué permite el subject

El subject permite librerías externas para ventana y eventos. Por eso una librería como GLFW puede encargarse de:

  • Crear la ventana.
  • Crear el contexto OpenGL.
  • Gestionar teclado, ratón y cierre de ventana.
  • Mantener el bucle de eventos.
  • Exponer glfwGetProcAddress, el punto de entrada para resolver funciones de OpenGL en runtime.

Pero no debe encargarse de las partes que el subject exige implementar o entender personalmente:

  • Parser de .obj.
  • Matrices y transformaciones.
  • Carga/compilación de shaders como caja negra externa.
  • Renderizador completo.
  • El cargador de funciones de OpenGL: conviene hacerlo a mano para poder defender que no se usan librerías externas más allá de la de ventana/eventos.

GLFW está permitido porque resuelve infraestructura de ventana/contexto/eventos, no el problema central de Scop.

3. Ventana, contexto y bucle mínimo

El esqueleto real que se escribió es:

glfwSetErrorCallback(error_callback);

if (!glfwInit())
    return 1;

glfwWindowHint(GLFW_CONTEXT_VERSION_MAJOR, 3);
glfwWindowHint(GLFW_CONTEXT_VERSION_MINOR, 3);
glfwWindowHint(GLFW_OPENGL_PROFILE, GLFW_OPENGL_CORE_PROFILE);

GLFWwindow *window = glfwCreateWindow(800, 600, "scop", NULL, NULL);
if (!window)
    return 1;

glfwMakeContextCurrent(window);

init_gl_functions();   /* el cargador manual */

while (!glfwWindowShouldClose(window))
{
    /* ... limpiar, dibujar ... */
    glfwSwapBuffers(window);
    glfwPollEvents();
}

glfwTerminate();

Dos detalles críticos de orden:

  • Los glfwWindowHint se llaman antes de glfwCreateWindow. La petición de contexto (versión y perfil) se formaliza en el instante de crear la ventana: los hints se consumen ahí y quedan fijados para la vida de esa ventana. Si se llaman después, crean un contexto con el perfil por defecto (legacy) y no se cambia retroactivamente.
  • glfwMakeContextCurrent(window) hace el contexto actual para el hilo. Sin contexto actual, llamadas como crear buffers, compilar shaders o limpiar la pantalla no tienen estado OpenGL válido sobre el que operar. El cargador manual va después de esta llamada, porque solo a partir de ahí glfwGetProcAddress devuelve punteros válidos del driver.

4. Por qué hay que cargar las funciones de OpenGL a mano

En Linux, las funciones de OpenGL 3.3+ no se exponen como símbolos normales enlazados en compilación. Se resuelven en runtime apuntando a direcciones de memoria del driver. La razón tiene dos capas:

  • El API de OpenGL es extensible por diseño: extensiones (GL_ARB_...) y vendors pueden añadir funciones que la librería base ni conoce. Las firmas de esas funciones futuras no existen en el momento de compilar, así que el punto de entrada (glfwGetProcAddress) no puede declarar un tipo concreto: devuelve un puntero genérico que luego se castea a la firma real de cada función.
  • La implementación la decide el driver de la GPU (Mesa, NVIDIA, AMD...) que se carga cuando se crea el contexto. Hasta que existe contexto no hay una dirección única y válida para cada función.

Por eso el flujo es: la librería de ventana crea el contexto, el conductor se carga con el contexto, y glfwGetProcAddress consulta al driver "dame tu implementación de tal función". El puntero-cast es el puente entre lo genérico del loader y lo concreto de cada firma.

5. El cargador manual: header, tipos y constantes

GLFW, por defecto, incluye <GL/gl.h> al incluir su header. Ese header del sistema declara algunas funciones legacy como símbolos reales (por ejemplo glClearColor, glClear, glDrawArrays). Si nosotros declaramos punteros a función con esos mismos nombres, el compilador responde: 'glClearColor' redeclared as different kind of symbol.

La solución canónica (la misma que usa GLAD) es evitar que GLFW meta gl.h y declarar nosotros los tipos y constantes mínimos que consumimos:

/* src/gl_loader.h */
#ifndef GL_LOADER_H
#define GL_LOADER_H

#include <stddef.h>
#include <stdint.h>

#define GLFW_INCLUDE_NONE          /* GLFW no incluye <GL/gl.h> */
#include <GLFW/glfw3.h>

typedef uint32_t   GLenum;
typedef uint32_t   GLbitfield;
typedef uint32_t   GLuint;
typedef int32_t    GLint;
typedef int32_t    GLsizei;
typedef uint8_t    GLboolean;
typedef uint8_t    GLubyte;
typedef float      GLfloat;
typedef char       GLchar;
typedef ptrdiff_t  GLsizeiptr;

enum {
    GL_COLOR_BUFFER_BIT = 0x00004000, /* glClear : buffer de color */
    GL_VERSION          = 0x1F02,     /* glGetString : versión */
    GL_FLOAT            = 0x1406,
    GL_FALSE            = 0,
    GL_VERTEX_SHADER    = 0x8B31,
    GL_FRAGMENT_SHADER  = 0x8B30,
    GL_ARRAY_BUFFER     = 0x8892,
    GL_STATIC_DRAW      = 0x88E4,
    GL_TRIANGLES        = 0x0004
};

void init_gl_functions(void);

extern void (*glClearColor)(GLfloat, GLfloat, GLfloat, GLfloat);
extern void (*glClear)(GLbitfield);
extern const GLubyte *(*glGetString)(GLenum);
/* ... resto de punteros a función con su firma exacta ... */

#endif

Un detalle que se pagó caro en la sesión: los valores de GL_COLOR_BUFFER_BIT y GL_VERSION son de la spec de Khronos, no inventados. Y en el enum, cada constante va separada por coma; olvidar una coma rompe la compilación.

6. Declarar, definir y asignar: las tres vidas de un puntero a función

El error de enlazado más instructivo de la sesión fue:

referencia a 'glClearColor' sin definir

Porque hay tres momentos distintos para un puntero a función global, y confundirlos rompe el build:

  • Declarar (extern void (*glClearColor)(...); en el header): "existe un símbolo con esta firma, será definido en otro lado". Repetible en cada archivo que lo necesite.
  • Definir (void (*glClearColor)(...); en el .c): reserva el almacenamiento real del símbolo. Debe existir exactamente una vez en todo el programa; si dos archivos definieran el mismo símbolo, el linker fallaría con multiple definition.
  • Asignar (glClearColor = (void *)glfwGetProcAddress("glClearColor");): ponerle un valor en runtime. Asignar no define: sin la definición previa, el símbolo no existe para el linker.

Las definiciones van en el .c del loader (no en el header, que solo declara). Con las definiciones en un solo .c, main y loader comparten las declaraciones del header, el .c posee el almacenamiento, e init_gl_functions() lo inicializa con las direcciones del driver.

Las asignaciones se hacen con una macro que también incluye el guard de error:

#define GL_LOAD(name)                                                       \
    do {                                                                    \
        name = (void *)glfwGetProcAddress(#name);                           \
        if (name == NULL) {                                                 \
            fprintf(stderr, "GL: %s no disponible (contexto core?)\n", #name); \
            exit(1);                                                        \
        }                                                                   \
    } while (0)

La macro resuelve dos problemas a la vez:

  • #name (stringification) convierte el nombre del parámetro en string para el mensaje de error, sin repetir el nombre a mano.
  • do { } while (0) hace que la macro se comporte como una sentencia normal y no rompa estructuras de control (if (x) GL_LOAD(a); else ...).
  • Las barras \ al final de cada línea pegan la macro en una sola directiva del preprocesador; deben ser el último carácter de la línea, sin espacios después, o la macro se corta y aparecen errores raros del tipo stray '#' in program.

El guard es obligatorio: si el driver no implementa una función (o el contexto no es core), glfwGetProcAddress devuelve NULL. Un programa que llamara a un puntero NULL crashearía sin aviso; el guard lo convierte en un mensaje claro y salida con código de error.

7. El primer triángulo

El dato mínimo es un array de posiciones hardcodeadas:

float vertices[] = {
    -0.5f, -0.5f, 0.0f,
     0.5f, -0.5f, 0.0f,
     0.0f,  0.5f, 0.0f,
};

Cada vértice tiene tres float:

x y z

Por tanto: 9 floats / 3 floats por vértice = 3 vértices.

Estos datos no aparecen en pantalla por estar en un array C. El GPU no lee automáticamente la RAM del programa; hay que subirlos a memoria del GPU:

GLuint vao, vbo;
glGenVertexArrays(1, &vao);
glBindVertexArray(vao);

glGenBuffers(1, &vbo);
glBindBuffer(GL_ARRAY_BUFFER, vbo);
glBufferData(GL_ARRAY_BUFFER, sizeof(vertices), vertices, GL_STATIC_DRAW);

glVertexAttribPointer(0, 3, GL_FLOAT, GL_FALSE, 3 * sizeof(float), (void *)0);
glEnableVertexAttribArray(0);
  • VBO (Vertex Buffer Object): guarda los datos crudos de vértices en memoria del GPU. Responde "¿dónde están los datos?".
  • VAO (Vertex Array Object): recuerda cómo se interpretan esos datos (location, tamaño, stride, offset). Responde "¿cómo se leen?".
  • glVertexAttribPointer conecta el dato con el shader: el atributo location 0 se lee con 3 floats por vértice, stride de 3 floats, offset 0.
  • (void *)0 es un offset en bytes desde el inicio del buffer, no un puntero real: es deuda histórica del API. Para un segundo atributo que empezara después de la posición, iría (void *)(3 * sizeof(float)).

Más adelante, cuando cada vértice tenga posición, color y UV, el VAO describirá tres atributos:

location 0: posición, 3 floats, offset 0
location 1: color,    3 floats, offset tras posición
location 2: UV,       2 floats, offset tras color

8. Shaders mínimos

Los shaders en esta clase van como strings; en el proyecto real se cargarán desde archivos con código propio.

const char *vs_src =
    "#version 330 core\n"
    "layout(location = 0) in vec3 aPos;\n"
    "void main() { gl_Position = vec4(aPos, 1.0); }\n";

const char *fs_src =
    "#version 330 core\n"
    "out vec4 FragColor;\n"
    "void main() { FragColor = vec4(0.8, 0.4, 0.2, 1.0); }\n";

La conexión importante es:

VAO dice:  location 0 contiene 3 floats por vértice
shader:    layout(location = 0) in vec3 aPos

Si el VAO configura location = 0 pero el shader espera location = 1, el shader está mirando otra entrada: puede no verse nada o leerse datos incorrectos.

El flujo de compilación y enlazado:

glCreateShader → glShaderSource → glCompileShader
glCreateProgram → glAttachShader(vertex) → glAttachShader(fragment) → glLinkProgram
glDeleteShader(vs) → glDeleteShader(fs) → glUseProgram

El subject no prohíbe escribir funciones propias como load_shader_file() o compile_shader(). Lo que no se debe hacer es delegar esa responsabilidad a una librería externa que oculte la carga, compilación, enlazado y reporte de errores. Además, en el proyecto real convendrá comprobar los errores de compilación con glGetShaderiv/glGetShaderInfoLog y los de enlazado con glGetProgramiv/glGetProgramInfoLog.

9. Dibujar cada frame

Un frame mínimo hace esto:

glClearColor(0.1f, 0.1f, 0.12f, 1.0f);
glClear(GL_COLOR_BUFFER_BIT);

glUseProgram(program);
glBindVertexArray(vao);
glDrawArrays(GL_TRIANGLES, 0, 3);

glfwSwapBuffers(window);
glfwPollEvents();

Responsabilidades:

FunciónResponsabilidad
glClearColorDefine el color con el que se limpiará el fondo.
glClearLimpia el framebuffer actual.
glUseProgramActiva el programa de shaders.
glBindVertexArrayActiva la receta para leer vértices. Rebindear cada frame es la convención que no falla: el binding del VAO es estado global de GL, y con varios objetos cada draw usa su receta.
glDrawArraysOrdena dibujar vértices secuenciales como triángulos.
glfwSwapBuffersMuestra el frame renderizado (doble buffer).
glfwPollEventsProcesa teclado, ratón, cierre, resize y otros eventos.

Si olvidas glfwPollEvents(), la ventana puede no responder a cierre, teclado o ratón. Si olvidas glfwSwapBuffers(), el frame no se presenta.

12. Predicciones y ejercicios

Conviene intentar cada ejercicio antes de consultar la solución.

Ejercicio 1 · contar vértices

Si vertices contiene 9 floats y cada vértice tiene 3 floats, ¿cuántos vértices hay?

Mostrar solución

Hay 3 vértices, porque 9 / 3 = 3.

Ejercicio 2 · quién carga las funciones de OpenGL

¿Quién carga las funciones de OpenGL en Linux y cómo?

Mostrar solución

El cargador las resuelve en runtime con glfwGetProcAddress para cada función, casteando el puntero genérico a la firma exacta. glfwGetProcAddress devuelve un puntero genérico; no puede devolver char* ni una firma concreta porque el API es extensible y las firmas futuras no existen al compilar.

Ejercicio 3 · el tipo del loader

¿Qué tipo devuelve glfwGetProcAddress y qué hay que hacer con él para poder llamar a la función?

Mostrar solución

Devuelve un puntero genérico a función. Hay que declarar un puntero con la firma exacta de la función y asignar el genérico con un cast. Sin el cast y la firma correcta, C no sabe cómo invocarla.

Ejercicio 4 · loader antes del contexto

¿Qué problema práctico aparece si llamas a init_gl_functions() antes de crear la ventana/contexto?

Mostrar solución

El driver aún no se ha cargado, así que glfwGetProcAddress devuelve NULL para las funciones 3.x y el guard de la macro aborta con un mensaje de error. La cadena correcta es: contexto primero, loader después.

Ejercicio 5 · la macro rota

Si olvidas las llaves \ al final de cada línea de la macro, ¿qué tipo de error de preprocesador aparece?

Mostrar solución

La macro se corta en la primera línea y el cuerpo queda suelto como código normal: errores del estilo expected identifier or '(' before 'do' y stray '#' in program por el # de la stringification. El \ debe ser el último carácter de la línea.

Ejercicio 6 · dónde se definen los punteros

¿Por qué las definiciones de los punteros van en el .c y no en el header?

Mostrar solución

Porque un símbolo se define una sola vez en todo el programa. Si dos .c definieran el mismo símbolo, el linker fallaría con multiple definition. En el header solo van las declaraciones extern, repetibles en cada archivo que las necesite.

Ejercicio 7 · qué imprime el driver

¿Qué esperas que imprima glGetString(GL_VERSION) si pediste un contexto 3.3 en un driver que soporta más?

Mostrar solución

Puede imprimir la versión exacta pedida (3.3) o la del contexto más nuevo que el driver decida crear (en la sesión real imprimió 4.6 (Core Profile) Mesa ...). Los hints piden el mínimo, no fijan el valor exacto.

Errores frecuentes
  • Pensar que GLFW resuelve el renderizador. Solo debe resolver ventana, contexto y eventos.
  • Creer que el contexto OpenGL contiene el modelo .obj. El modelo vive en CPU y luego se sube a buffers.
  • Confundir VBO y VAO: el VBO guarda datos; el VAO describe cómo leerlos.
  • Configurar un location en el VAO y otro distinto en el shader.
  • Olvidar comprobar errores de compilación y enlazado de shaders.
  • Olvidar glfwPollEvents() y obtener una ventana que no responde.
  • Olvidar glfwSwapBuffers() y no presentar correctamente el frame.
  • Creer que el triángulo hardcodeado es parte del proyecto final; solo es una prueba mínima del pipeline.
  • Usar el cargador manual antes de glfwMakeContextCurrent.
  • Poner los glfwWindowHint después de glfwCreateWindow: el contexto nace con el perfil por defecto.
  • Olvidar las comas en el enum de constantes y ver errores de declaración confusos.
  • Olvidar las definiciones de los punteros en el .c y sufrir undefined reference en el enlazado.
  • Dejar espacios después de las \ de la macro y ver stray '#' in program.
  • Confundir (void *)0 de glVertexAttribPointer con un puntero real, cuando es un offset en bytes.

Has aprendido que

  • Antes de dibujar necesitas ventana, contexto OpenGL actual, shaders, buffers y bucle de render.
  • GLFW está permitido porque gestiona ventana, contexto y eventos, no el parser ni las matemáticas del renderer.
  • OpenGL necesita un contexto actual antes de ejecutar llamadas válidas.
  • Las funciones de OpenGL se resuelven en runtime con glfwGetProcAddress porque el API es extensible y el driver se carga con el contexto; no hay símbolos enlazables para OpenGL 3.3+.
  • GLFW_INCLUDE_NONE evita que GLFW meta <GL/gl.h> y choque con nuestros punteros a función.
  • Extern declara, el .c define, y la asignación en runtime llena el valor; los tres momentos son distintos.
  • La macro GL_LOAD con #name y do { } while (0) carga cada función y aborta con mensaje claro si el driver no la da.
  • El VBO contiene datos; el VAO recuerda cómo leerlos; layout(location = N) debe coincidir con glVertexAttribPointer.
  • El vertex shader trabaja por vértice; el fragment shader decide colores por fragmento.
  • glDrawArrays(GL_TRIANGLES, 0, 3) dibuja tres vértices secuenciales como un triángulo.
  • glfwSwapBuffers() presenta el frame terminado y glfwPollEvents() procesa eventos.
  • Pedir un contexto 3.3 pide un mínimo, no un valor exacto: el driver puede entregar una versión mayor compatible.

Objective

Set up the real Scop skeleton on which all the other classes will be built: a GLFW window, an OpenGL context, a manual OpenGL function loader, minimal shaders, VBO/VAO and a render loop. By the end of this class you must be able to explain what GLFW provides, what an OpenGL context is and why it must be current, why OpenGL functions must be loaded at runtime instead of linked, the difference between declaring, defining and assigning a function pointer, how the shader attributes connect to the buffer data, and why the render loop needs glfwSwapBuffers() and glfwPollEvents().

1. What we are isolating

This class does not load .obj files yet, does not use MVP matrices and does not apply textures. It isolates two questions:

1. What must exist before the GPU can draw anything?
2. How do you obtain the OpenGL functions the GPU will execute?

The minimum flow is:

program
  ↓
initialize window library (glfwInit)
  ↓
request a core 3.3 context (glfwWindowHint BEFORE creating the window)
  ↓
create window + OpenGL context (glfwCreateWindow)
  ↓
make the context current (glfwMakeContextCurrent)
  ↓

  ↓

The window is not the scene. It is the destination where OpenGL will present the final framebuffer.

2. What the subject allows

The subject allows external libraries for the window and events. That is why a library like GLFW may take care of:

  • Creating the window.
  • Creating the OpenGL context.
  • Handling keyboard, mouse and window close.
  • Running the event loop.
  • Exposing glfwGetProcAddress, the entry point to resolve OpenGL functions at runtime.

But it must not take care of the parts the subject requires you to implement or understand yourself:

  • The .obj parser.
  • Matrices and transformations.
  • Shader loading/compilation as an external black box.
  • The full renderer.
  • The OpenGL loader: do it by hand so you can defend that no external libraries are used beyond the window/event one.

GLFW is allowed because it solves window/context/event infrastructure, not the core problem of Scop.

3. Window, context and minimal loop

The real skeleton that was written is:

glfwSetErrorCallback(error_callback);

if (!glfwInit())
    return 1;

glfwWindowHint(GLFW_CONTEXT_VERSION_MAJOR, 3);
glfwWindowHint(GLFW_CONTEXT_VERSION_MINOR, 3);
glfwWindowHint(GLFW_OPENGL_PROFILE, GLFW_OPENGL_CORE_PROFILE);

GLFWwindow *window = glfwCreateWindow(800, 600, "scop", NULL, NULL);
if (!window)
    return 1;

glfwMakeContextCurrent(window);

init_gl_functions();   /* the manual loader */

while (!glfwWindowShouldClose(window))
{
    /* ... clear, draw ... */
    glfwSwapBuffers(window);
    glfwPollEvents();
}

glfwTerminate();

Two critical ordering details:

  • The glfwWindowHint calls come before glfwCreateWindow. The context request (version and profile) is finalized at the moment the window is created: the hints are consumed then and stay fixed for that window's lifetime. If called afterwards, the context is born with the default profile (legacy) and cannot be changed retroactively.
  • glfwMakeContextCurrent(window) makes the context current for the thread. Without a current context, calls like creating buffers, compiling shaders or clearing the screen have no valid OpenGL state to operate on. The manual loader goes after this call, because only from that point on glfwGetProcAddress returns valid driver pointers.

4. Why OpenGL functions must be loaded by hand

On Linux, OpenGL 3.3+ functions are not exposed as normal symbols linked at compile time. They are resolved at runtime by pointing to driver memory addresses. The reason has two layers:

  • The OpenGL API is extensible by design: extensions (GL_ARB_...) and vendors can add functions the base library does not even know about. The signatures of those future functions do not exist at compile time, so the entry point (glfwGetProcAddress) cannot declare a concrete type: it returns a generic pointer that is later cast to each function's real signature.
  • The implementation is decided by the GPU driver (Mesa, NVIDIA, AMD...) which loads when the context is created. Until a context exists there is no single valid address for each function.

That is why the flow is: the window library creates the context, the driver loads with the context, and glfwGetProcAddress asks the driver "give me your implementation of this function". The pointer cast is the bridge between the generic loader and the concrete signature.

5. The manual loader: header, types and constants

By default, GLFW includes <GL/gl.h> when you include its header. That system header declares some legacy functions as real symbols (for example glClearColor, glClear, glDrawArrays). If we declare function pointers with those same names, the compiler answers: 'glClearColor' redeclared as different kind of symbol.

The canonical solution (the same one used by GLAD) is to stop GLFW from including gl.h and declare the minimal types and constants we consume ourselves:

/* src/gl_loader.h */
#ifndef GL_LOADER_H
#define GL_LOADER_H

#include <stddef.h>
#include <stdint.h>

#define GLFW_INCLUDE_NONE          /* GLFW does not include <GL/gl.h> */
#include <GLFW/glfw3.h>

typedef uint32_t   GLenum;
typedef uint32_t   GLbitfield;
typedef uint32_t   GLuint;
typedef int32_t    GLint;
typedef int32_t    GLsizei;
typedef uint8_t    GLboolean;
typedef uint8_t    GLubyte;
typedef float      GLfloat;
typedef char       GLchar;
typedef ptrdiff_t  GLsizeiptr;

enum {
    GL_COLOR_BUFFER_BIT = 0x00004000, /* glClear : color buffer */
    GL_VERSION          = 0x1F02,     /* glGetString : version */
    GL_FLOAT            = 0x1406,
    GL_FALSE            = 0,
    GL_VERTEX_SHADER    = 0x8B31,
    GL_FRAGMENT_SHADER  = 0x8B30,
    GL_ARRAY_BUFFER     = 0x8892,
    GL_STATIC_DRAW      = 0x88E4,
    GL_TRIANGLES        = 0x0004
};

void init_gl_functions(void);

extern void (*glClearColor)(GLfloat, GLfloat, GLfloat, GLfloat);
extern void (*glClear)(GLbitfield);
extern const GLubyte *(*glGetString)(GLenum);
/* ... the rest of the function pointers with their exact signatures ... */

#endif

One detail that cost time in the session: the GL_COLOR_BUFFER_BIT and GL_VERSION values come from the Khronos spec, they are not invented. And in the enum, each constant is separated by a comma; forgetting a comma breaks the build.

6. Declare, define and assign: the three lives of a function pointer

The most instructive linking error of the session was:

reference to 'glClearColor' undefined

Because there are three different moments for a global function pointer, and confusing them breaks the build:

  • Declare (extern void (*glClearColor)(...); in the header): "a symbol with this signature exists, it will be defined elsewhere". Repeatable in every file that needs it.
  • Define (void (*glClearColor)(...); in the .c): reserves the real storage of the symbol. It must exist exactly once in the whole program; if two files defined the same symbol, the linker would fail with multiple definition.
  • Assign (glClearColor = (void *)glfwGetProcAddress("glClearColor");): give it a value at runtime. Assigning is not defining: without the previous definition, the symbol does not exist for the linker.

The definitions live in the loader's .c file (not in the header, which only declares). With the definitions in a single .c, main and loader share the header declarations, the .c owns the storage, and init_gl_functions() initializes it with the driver addresses.

The assignments are made with a macro that also includes the error guard:

#define GL_LOAD(name)                                                       \
    do {                                                                    \
        name = (void *)glfwGetProcAddress(#name);                           \
        if (name == NULL) {                                                 \
            fprintf(stderr, "GL: %s not available (core context?)\n", #name); \
            exit(1);                                                        \
        }                                                                   \
    } while (0)

The macro solves two problems at once:

  • #name (stringification) turns the parameter name into a string for the error message, without repeating the name by hand.
  • do { } while (0) makes the macro behave like a normal statement and does not break control structures (if (x) GL_LOAD(a); else ...).
  • The backslashes \ at the end of each line join the macro into a single preprocessor directive; they must be the last character of the line, with no trailing space, or the macro breaks and you see odd errors like stray '#' in program.

The guard is mandatory: if the driver does not implement a function (or the context is not core), glfwGetProcAddress returns NULL. A program that called a NULL pointer would crash without warning; the guard turns it into a clear message and an error exit code.

7. The first triangle

The minimal data is an array of hardcoded positions:

float vertices[] = {
    -0.5f, -0.5f, 0.0f,
     0.5f, -0.5f, 0.0f,
     0.0f,  0.5f, 0.0f,
};

Each vertex has three floats:

x y z

Therefore: 9 floats / 3 floats per vertex = 3 vertices.

These data do not show up on screen just because they are in a C array. The GPU does not automatically read your program's RAM; you must upload them to GPU memory:

GLuint vao, vbo;
glGenVertexArrays(1, &vao);
glBindVertexArray(vao);

glGenBuffers(1, &vbo);
glBindBuffer(GL_ARRAY_BUFFER, vbo);
glBufferData(GL_ARRAY_BUFFER, sizeof(vertices), vertices, GL_STATIC_DRAW);

glVertexAttribPointer(0, 3, GL_FLOAT, GL_FALSE, 3 * sizeof(float), (void *)0);
glEnableVertexAttribArray(0);
  • VBO (Vertex Buffer Object): holds the raw vertex data in GPU memory. It answers "where is the data?"
  • VAO (Vertex Array Object): remembers how to interpret that data (location, size, stride, offset). It answers "how is it read?"
  • glVertexAttribPointer connects the data with the shader: attribute location 0 is read as 3 floats per vertex, stride of 3 floats, offset 0.
  • (void *)0 is a byte offset from the start of the buffer, not a real pointer: it is historical API debt. A second attribute starting right after the position would use (void *)(3 * sizeof(float)).

Later, when each vertex has position, color and UV, the VAO will describe three attributes:

location 0: position, 3 floats, offset 0
location 1: color,    3 floats, offset after position
location 2: UV,       2 floats, offset after color

8. Minimal shaders

In this class the shaders live as strings; in the real project they will be loaded from files with your own code.

const char *vs_src =
    "#version 330 core\n"
    "layout(location = 0) in vec3 aPos;\n"
    "void main() { gl_Position = vec4(aPos, 1.0); }\n";

const char *fs_src =
    "#version 330 core\n"
    "out vec4 FragColor;\n"
    "void main() { FragColor = vec4(0.8, 0.4, 0.2, 1.0); }\n";

The important connection is:

VAO says:  location 0 holds 3 floats per vertex
shader:    layout(location = 0) in vec3 aPos

If the VAO configures location = 0 but the shader expects location = 1, the shader is looking at another input: nothing may be visible or wrong data may be read.

The compile and link flow:

glCreateShader → glShaderSource → glCompileShader
glCreateProgram → glAttachShader(vertex) → glAttachShader(fragment) → glLinkProgram
glDeleteShader(vs) → glDeleteShader(fs) → glUseProgram

The subject does not forbid writing your own functions such as load_shader_file() or compile_shader(). What you must not do is delegate that responsibility to an external library that hides loading, compilation, linking and error reporting. In the real project you will also want to check compile errors with glGetShaderiv/glGetShaderInfoLog and linking errors with glGetProgramiv/glGetProgramInfoLog.

9. Drawing each frame

A minimal frame does this:

glClearColor(0.1f, 0.1f, 0.12f, 1.0f);
glClear(GL_COLOR_BUFFER_BIT);

glUseProgram(program);
glBindVertexArray(vao);
glDrawArrays(GL_TRIANGLES, 0, 3);

glfwSwapBuffers(window);
glfwPollEvents();

Responsibilities:

FunctionResponsibility
glClearColorSets the color used to clear the background.
glClearClears the current framebuffer.
glUseProgramActivates the shader program.
glBindVertexArrayActivates the recipe for reading vertices. Rebinding it every frame is the convention that never fails: the VAO binding is global GL state, and with several objects each draw uses its own recipe.
glDrawArraysTells the GPU to draw sequential vertices as triangles.
glfwSwapBuffersShows the rendered frame (double buffering).
glfwPollEventsProcesses keyboard, mouse, close, resize and other events.

If you forget glfwPollEvents(), the window may stop responding to close, keyboard or mouse. If you forget glfwSwapBuffers(), the frame is never presented.

12. Predictions and exercises

Try each exercise before checking the answer.

Exercise 1 · counting vertices

If vertices holds 9 floats and each vertex has 3 floats, how many vertices are there?

Show answer

There are 3 vertices, because 9 / 3 = 3.

Exercise 2 · who loads OpenGL functions

Who loads the OpenGL functions on Linux, and how?

Show answer

The loader resolves them at runtime with glfwGetProcAddress for each function, casting the generic pointer to the exact signature. glfwGetProcAddress returns a generic pointer; it cannot return char* or a concrete signature because the API is extensible and future signatures do not exist at compile time.

Exercise 3 · the loader's type

What type does glfwGetProcAddress return, and what do you have to do to it before you can call the function?

Show answer

It returns a generic function pointer. You must declare a pointer with the exact signature of the function and assign the generic pointer to it with a cast. Without the cast and the correct signature, C does not know how to invoke it.

Exercise 4 · loader before the context

What practical problem appears if you call init_gl_functions() before creating the window/context?

Show answer

The driver has not loaded yet, so glfwGetProcAddress returns NULL for the 3.x functions and the macro guard aborts with an error message. The correct chain is: context first, loader after.

Exercise 5 · the broken macro

If you forget the backslashes \ at the end of each macro line, what kind of preprocessor error appears?

Show answer

The macro is cut at the first line and the body stays loose as regular code: errors like expected identifier or '(' before 'do' and stray '#' in program because of the stringification #. The \ must be the last character of the line.

Exercise 6 · where the pointers are defined

Why do the pointer definitions go in the .c file and not in the header?

Show answer

Because a symbol is defined only once across the whole program. If two .c files defined the same symbol, the linker would fail with multiple definition. The header only carries extern declarations, repeatable in every file that needs them.

Exercise 7 · what the driver prints

What do you expect glGetString(GL_VERSION) to print if you requested a 3.3 context on a driver that supports more?

Show answer

It may print the exact requested version (3.3) or the newest context the driver decides to create (in the real session it printed 4.6 (Core Profile) Mesa ...). The hints request the minimum, they do not fix the exact value.

Common mistakes
  • Thinking that GLFW solves the renderer. It should only solve window, context and events.
  • Believing the OpenGL context holds the .obj model. The model lives in CPU and is later uploaded to buffers.
  • Confusing VBO and VAO: the VBO stores data; the VAO describes how to read it.
  • Setting one location in the VAO and a different one in the shader.
  • Forgetting to check shader compilation and linking errors.
  • Forgetting glfwPollEvents() and getting a window that does not respond.
  • Forgetting glfwSwapBuffers() and not presenting the frame correctly.
  • Believing the hardcoded triangle is part of the final project; it is only a minimal pipeline test.
  • Using the manual loader before glfwMakeContextCurrent.
  • Putting the glfwWindowHint calls after glfwCreateWindow: the context is born with the default profile.
  • Forgetting the commas in the constants enum and seeing confusing declaration errors.
  • Forgetting the pointer definitions in the .c and getting an undefined reference at link time.
  • Leaving spaces after the macro's \ and seeing stray '#' in program.
  • Treating (void *)0 of glVertexAttribPointer as a real pointer when it is a byte offset.

You have learned that

  • Before drawing you need a window, a current OpenGL context, shaders, buffers and a render loop.
  • GLFW is allowed because it handles window, context and events, not the parser or the renderer math.
  • OpenGL needs a current context before running valid calls.
  • OpenGL functions are resolved at runtime with glfwGetProcAddress because the API is extensible and the driver loads with the context; there are no linkable symbols for OpenGL 3.3+.
  • GLFW_INCLUDE_NONE stops GLFW from pulling in <GL/gl.h> and colliding with our function pointers.
  • Extern declares, the .c defines, and the runtime assignment fills the value; the three moments are different.
  • The GL_LOAD macro with #name and do { } while (0) loads each function and aborts with a clear message if the driver does not provide it.
  • The VBO holds data; the VAO remembers how to read it; layout(location = N) must match glVertexAttribPointer.
  • The vertex shader works per vertex; the fragment shader decides colors per fragment.
  • glDrawArrays(GL_TRIANGLES, 0, 3) draws three sequential vertices as a triangle.
  • glfwSwapBuffers() presents the finished frame and glfwPollEvents() processes events.
  • Requesting a 3.3 context asks for a minimum, not an exact value: the driver may deliver a newer compatible version.
