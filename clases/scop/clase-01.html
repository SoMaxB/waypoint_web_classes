2. Un .obj no es una imagen

Un archivo .obj es texto que describe geometría. No contiene píxeles ya preparados para pantalla.

Ejemplo mínimo:

v -0.5 -0.5 0.0
v  0.5 -0.5 0.0
v  0.0  0.5 0.0
f 1 2 3

Las líneas v definen posiciones de vértices. La línea f define una cara usando índices hacia esos vértices.

El parser del .obj transforma texto en datos:

texto .obj
  ↓
lista de posiciones
  ↓
lista de caras
  ↓
lista de triángulos
  ↓
buffer que el GPU pueda leer

Si el archivo contiene:

v 0 0 0
v 1 0 0
v 1 1 0
v 0 1 0
f 1 2 3 4

el parser podría producir:

positions:
  0: (0, 0, 0)
  1: (1, 0, 0)
  2: (1, 1, 0)
  3: (0, 1, 0)

triangles:
  (0, 1, 2)
  (0, 2, 3)

Hay dos conversiones importantes:

  • La cara de cuatro vértices se convierte en dos triángulos.
  • Los índices OBJ, que son base uno, se convierten a índices de array base cero.

3. Caras, triángulos e índices

El GPU suele dibujar con GL_TRIANGLES: cada grupo de tres vértices forma un triángulo. Por eso una cara con cuatro vértices no se puede enviar directamente como si fuera un triángulo.

Una conversión típica es la triangulación en abanico:

f 1 2 3 4

se convierte en:

triángulo 1: 1 2 3
triángulo 2: 1 3 4

Visualmente:

4 ----- 3
|     / |
|   /   |
| /     |
1 ----- 2

Para una cara con más vértices:

f 1 2 3 4 5

la triangulación en abanico produce:

1 2 3
1 3 4
1 4 5

Esto funciona bien para polígonos simples y convexos. Puede fallar con caras cóncavas o no coplanares, que precisamente entran en la frontera de los .obj complejos mencionados en el bonus.

El otro detalle crítico es que OBJ usa índices base uno. Si el archivo dice:

f 3 7 10

en un array C/C++/Rust debes leer:

vertices[2]
vertices[6]
vertices[9]

Si olvidas restar 1, el modelo queda mal conectado o puedes acceder fuera del array.

4. Del modelo a la pantalla

Las coordenadas del .obj no van directas a píxeles. Pasan por transformaciones:

posición local del modelo
  ↓ model
posición en el mundo
  ↓ view
posición vista desde la cámara
  ↓ projection
posición en perspectiva
  ↓ viewport
píxeles en la ventana

La composición habitual es:

final = Projection * View * Model * Vertex

Cada matriz tiene una responsabilidad:

MatrizResponsabilidad
ModelMover, rotar o escalar el objeto desde su espacio local.
ViewRepresentar la cámara: desde dónde se mira y hacia dónde.
ProjectionAplicar perspectiva para que la profundidad afecte al tamaño aparente.

En Scop es especialmente importante el centro del objeto. El subject pide que el 42 logo gire sobre su eje central, no sobre una esquina. Si el modelo está lejos del origen y rotas alrededor del origen, el objeto orbita.

Para centrar un modelo se puede calcular su caja envolvente:

1. leer todos los vértices
2. calcular min_x, max_x, min_y, max_y, min_z, max_z
3. calcular centro:
   cx = (min_x + max_x) / 2
   cy = (min_y + max_y) / 2
   cz = (min_z + max_z) / 2
4. restar ese centro a cada vértice

Ejemplo:

vértice original: (10, 2, 0)
centro calculado: (10, 0, 0)
vértice centrado: (0, 2, 0)

Ahora una rotación alrededor de (0,0,0) hace que el objeto gire sobre su propio centro.

5. Perspectiva

Sin perspectiva, una escena puede verse plana: un objeto lejos puede tener el mismo tamaño aparente que uno cercano. En perspectiva, lo lejano se ve más pequeño.

La matriz Projection prepara esa transformación. La idea que debes retener ahora es:

más lejos en z
  ↓
w más grande
  ↓
x/w e y/w más pequeños
  ↓
se ve más pequeño

No hace falta memorizar todavía la fórmula completa de una matriz de perspectiva. Lo importante para esta primera clase es entender que Scop pide una proyección en perspectiva real, no solo dibujar coordenadas en pantalla.

6. Shaders y framebuffer

En OpenGL moderno, el GPU ejecuta pequeños programas llamados shaders.

El vertex shader corre una vez por vértice. Su trabajo principal en Scop será transformar la posición:

gl_Position = mvp * vec4(aPos, 1.0);

Traducido:

toma la posición local del vértice
la convierte en coordenada homogénea
aplica Model/View/Projection
devuelve la posición final al pipeline

El fragment shader corre después de la rasterización. Su trabajo es decidir el color final de cada fragmento:

FragColor = vec4(0.7, 0.7, 0.7, 1.0);

Más adelante también mezclará color y textura:

FragColor = mix(faceColor, texColor, textureFactor);

Donde:

textureFactor = 0.0  ->  solo color
textureFactor = 1.0  ->  solo textura
textureFactor = 0.5  ->  mitad color, mitad textura

La rasterización es la etapa intermedia que convierte triángulos transformados en fragmentos candidatos a píxeles. El framebuffer guarda la imagen final que se mostrará en la ventana.

7. Transición suave color/textura

El subject no pide solo una tecla que cambie entre color y textura. Pide una transición suave.

Un cambio brusco sería:

frame actual: textureFactor = 0.0
tecla pulsada
frame siguiente: textureFactor = 1.0

Eso es un corte. La idea correcta es que la tecla cambie el objetivo, y cada frame acerque el valor actual poco a poco:

textureFactor = 0.00
textureFactor = 0.08
textureFactor = 0.16
textureFactor = 0.24
...
textureFactor = 1.00

El fragment shader mezcla con ese factor:

mix(faceColor, texColor, textureFactor)

Así la textura aparece o desaparece progresivamente.

Ejercicio 1 · cara de cuatro vértices

Si el .obj contiene una cara f 1 2 3 4, ¿qué problema aparece si el GPU dibuja con GL_TRIANGLES?

Mostrar solución

La cara tiene cuatro vértices, pero un triángulo tiene tres. Hay que convertirla en triángulos, por ejemplo (1,2,3) y (1,3,4).

Ejercicio 2 · índices base uno

Si el .obj tiene f 3 7 10, ¿qué índices de un array C/C++ debes leer?

Mostrar solución

Debes leer 2, 6 y 9, porque OBJ usa índices base uno y los arrays normales usan base cero.

Ejercicio 3 · tamaño del triángulo

Si cambias los vértices de un triángulo de (0,0,0), (1,0,0), (1,1,0) a (0,0,0), (2,0,0), (2,2,0), ¿qué cambia en pantalla?

Mostrar solución

El triángulo se hace más grande, porque sus posiciones ocupan más espacio en el sistema de coordenadas.

Ejercicio 4 · modelo descentrado

Si un cuadrado tiene su centro real en (10,0,0) y lo rotas alrededor del origen sin centrarlo antes, ¿qué verás?

Mostrar solución

El objeto orbitará alrededor del origen, como si estuviera atado a una cuerda. No girará sobre su propio centro.

Ejercicio 5 · tamaño aparente

Si dos triángulos tienen el mismo tamaño real, pero uno está más lejos de la cámara, ¿qué debería pasar en perspectiva?

Mostrar solución

El triángulo lejano debe verse más pequeño.

Ejercicio 6 · transición en un frame

Si al pulsar una tecla cambias textureFactor de 0.0 a 1.0 en un solo frame, ¿cumples la transición suave?

Mostrar solución

No. Eso es un corte brusco. La tecla debe cambiar el objetivo y el valor actual debe acercarse gradualmente cada frame.

2. A .obj is not an image

An .obj file is text that describes geometry. It contains no screen-ready pixels.

Minimal example:

v -0.5 -0.5 0.0
v  0.5 -0.5 0.0
v  0.0  0.5 0.0
f 1 2 3

The v lines define vertex positions. The f line defines a face using indices into those vertices.

The .obj parser turns text into data:

.obj text
  ↓
list of positions
  ↓
list of faces
  ↓
list of triangles
  ↓
buffer the GPU can read

If the file contains:

v 0 0 0
v 1 0 0
v 1 1 0
v 0 1 0
f 1 2 3 4

the parser could produce:

positions:
  0: (0, 0, 0)
  1: (1, 0, 0)
  2: (1, 1, 0)
  3: (0, 1, 0)

triangles:
  (0, 1, 2)
  (0, 2, 3)

There are two important conversions:

  • The four-vertex face is converted into two triangles.
  • OBJ indices, which are one-based, are converted to zero-based array indices.

3. Faces, triangles and indices

The GPU usually draws with GL_TRIANGLES: every group of three vertices forms a triangle. That is why a face with four vertices cannot be sent directly as if it were a triangle.

A typical conversion is fan triangulation:

f 1 2 3 4

becomes:

triangle 1: 1 2 3
triangle 2: 1 3 4

Visually:

4 ----- 3
|     / |
|   /   |
| /     |
1 ----- 2

For a face with more vertices:

f 1 2 3 4 5

fan triangulation produces:

1 2 3
1 3 4
1 4 5

This works well for simple convex polygons. It can fail with concave or non-coplanar faces, which is exactly the boundary of the complex .obj files mentioned in the bonus.

The other critical detail is that OBJ uses one-based indices. If the file says:

f 3 7 10

in a C/C++/Rust array you must read:

vertices[2]
vertices[6]
vertices[9]

If you forget to subtract 1, the model ends up badly connected or you may access outside the array.

4. From the model to the screen

The .obj coordinates do not go straight to pixels. They go through transformations:

model local position
  ↓ model
world position
  ↓ view
position seen from the camera
  ↓ projection
position in perspective
  ↓ viewport
pixels in the window

The usual composition is:

final = Projection * View * Model * Vertex

Each matrix has a responsibility:

MatrixResponsibility
ModelMove, rotate or scale the object from its local space.
ViewRepresent the camera: where you look from and where you look at.
ProjectionApply perspective so depth affects the apparent size.

In Scop the center of the object is especially important. The subject requires the 42 logo to spin on its central axis, not around a corner. If the model sits far from the origin and you rotate around the origin, the object orbits.

To center a model you can compute its bounding box:

1. read all vertices
2. compute min_x, max_x, min_y, max_y, min_z, max_z
3. compute center:
   cx = (min_x + max_x) / 2
   cy = (min_y + max_y) / 2
   cz = (min_z + max_z) / 2
4. subtract that center from every vertex

Example:

original vertex: (10, 2, 0)
computed center: (10, 0, 0)
centered vertex: (0, 2, 0)

Now a rotation around (0,0,0) makes the object spin on its own center.

5. Perspective

Without perspective a scene can look flat: a distant object may have the same apparent size as a nearby one. With perspective, distant things look smaller.

The Projection matrix prepares that transformation. The idea to keep now is:

farther in z
  ↓
w larger
  ↓
x/w and y/w smaller
  ↓
looks smaller

You do not need to memorize the full perspective matrix formula yet. What matters for this first class is understanding that Scop asks for a real perspective projection, not just drawing coordinates on screen.

6. Shaders and framebuffer

In modern OpenGL the GPU runs small programs called shaders.

The vertex shader runs once per vertex. Its main job in Scop will be to transform the position:

gl_Position = mvp * vec4(aPos, 1.0);

Translated:

take the vertex local position
turn it into a homogeneous coordinate
apply Model/View/Projection
give the final position back to the pipeline

The fragment shader runs after rasterization. Its job is to decide the final color of each fragment:

FragColor = vec4(0.7, 0.7, 0.7, 1.0);

Later it will also blend color and texture:

FragColor = mix(faceColor, texColor, textureFactor);

Where:

textureFactor = 0.0  ->  only color
textureFactor = 1.0  ->  only texture
textureFactor = 0.5  ->  half color, half texture

Rasterization is the intermediate stage that turns transformed triangles into fragments (pixel candidates). The framebuffer stores the final image that will be shown in the window.

7. Smooth color/texture transition

The subject does not ask only for a key that switches between color and texture. It asks for a smooth transition.

An abrupt change would be:

current frame: textureFactor = 0.0
key pressed
next frame: textureFactor = 1.0

That is a cut. The correct idea is that the key changes the target, and each frame moves the current value gradually:

textureFactor = 0.00
textureFactor = 0.08
textureFactor = 0.16
textureFactor = 0.24
...
textureFactor = 1.00

The fragment shader blends with that factor:

mix(faceColor, texColor, textureFactor)

That way the texture appears or disappears progressively.

Common mistakes
  • Thinking that a .obj is an image. It is geometry in text, not pixels.
  • Sending faces with four or more vertices as if they were triangles.
  • Forgetting that OBJ indices are one-based and using them directly as array indices.
  • Rotating an uncentered model and getting an orbit instead of a spin on its axis.
  • Treating Model, View and Projection as one indistinguishable transformation.
  • Believing that drawing something on screen already satisfies the subject's perspective requirement.
  • Switching from color to texture in a single frame and calling it a smooth transition.
  • Using external libraries to load .obj files, create matrices or load shaders, which contradicts the subject constraints.

You have learned that

  • Scop is a defensible mini-renderer, not an improvised visual demo.
  • An .obj describes vertices, faces and other attributes; your parser turns it into internal data.
  • The GPU usually draws triangles, so faces with more vertices must be triangulated.
  • OBJ indices start at 1, but arrays start at 0.
  • The pipeline transforms vertices with Model, View and Projection before they reach the screen.
  • Centering the model is key for it to rotate around its central axis.
  • Perspective makes distant things look smaller thanks to the projection and the division by w.
  • The vertex shader transforms vertices; the fragment shader decides colors.
  • A smooth color/texture transition is achieved by gradually interpolating a factor, not by an instant change.
