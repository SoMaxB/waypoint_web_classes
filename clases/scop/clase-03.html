Objetivo

Convertir texto en geometría: leer un .obj real con fgets, validar cada línea v y f, traducir índices base 1 a base 0, trocear caras de N vértices en N−2 triángulos con abanico y subir el resultado a VBO/EBO. Al terminar debes poder explicar por qué un .obj no es una imagen, por qué f 1 2 3 4 no es un triángulo, dónde se rompe el parser si olvidas -1, cómo dos pasadas evitan pelearte con realloc, por qué f 1/2/3 solo te interesa el 1, y por qué el EBO vive dentro del VAO y necesita GL_DEPTH_TEST.

Esta clase se tomó de forma interactiva y cumple la regla del proyecto: se escribió, compiló con -Wall -Wextra -Werror y ejecutó código real. El resultado observable fue OBJ OK: 8 vertices (24 floats), 36 indices (12 triangulos) y un cubo naranja renderizado con glDrawElements en vez del triángulo hardcodeado, sin avisos de compilación y con el cubo validado índice a índice.

1. Qué estamos aislando

Esta clase no toca matrices MVP ni texturas. Aísla una sola pregunta:

¿Cómo pasa una línea como "f 1 2 3 4" del disco a triángulos que el GPU entiende?

El flujo mínimo es:

assets/cube.obj (texto)
  ↓ fgets línea a línea
pasada 1: contar v y caras → reservar exacto
  ↓ malloc + rewind
pasada 2: llenar vertices[] y indices[] (base 0, fan)
  ↓
t_mesh { vertices, v_count, indices, i_count }
  ↓ glBufferData(GL_ARRAY_BUFFER) + glBufferData(GL_ELEMENT_ARRAY_BUFFER)
VAO (location 0 = 3 floats, stride 3*sizeof(float), offset 0)
  ↓
glDrawElements(GL_TRIANGLES, 36, GL_UNSIGNED_INT, 0)

El parser es tonto a propósito: solo convierte texto en geometría. Centrar el modelo, proyectar y texturizar vendrán después.

3. fgets, sscanf y la trampa de v

Para texto línea a línea fopen + fgets evita reimplementar buffering:

FILE *fp = fopen(path, "r");
char line[1024];
while (fgets(line, sizeof(line), fp)) {
    const char *s = skip_ws(line);
    if (*s == '\0' || *s == '\n' || *s == '#') continue;
    // ...
}

open/read te da trozos crudos sin garantía de que un trozo acabe en \n; fgets te da una línea completa por llamada.

Para v basta sscanf porque el formato es fijo:

float x, y, z;
if (sscanf(s, "v %f %f %f", &x, &y, &z) != 3) error;

El retorno de sscanf es tu validación gratis: pedir 3 y recibir 2 significa línea rota. Y OJO: lo robusto es filtrar antes por prefijo, no fiarte solo de sscanf:

if (s[0]=='v' && s[1]==' ') { /* v pura */ }
else if (s[0]=='v' && s[1]=='t') continue;
else if (s[0]=='v' && s[1]=='n') continue;

Para f no sirve sscanf con 8 %d fijos — un quad tiene 4 índices (==4 nunca es ==8) y Blender escupe 1/2/3 o 1//3. Hay que tokenizar:

int tmp[64]; int n=0; const char *p = s+2; // tras "f "
while (*p && *p!='#' && n<64) {
    char *end; long v = strtol(p, &end, 10);
    if (end==p) break;
    tmp[n++] = (int)v;
    p = end;
    while (*p && *p!=' ' && *p!='\t' && *p!='\n') p++; // salta "/2/3"
    p = skip_ws(p);
}

strtol para en /, así 1/2/3 te deja el 1 y el bucle salta el resto hasta el espacio.

4. Dos pasadas vs realloc

No sabes cuántos v trae el archivo antes de leerlo. Dos estrategias:

  • Dos pasadas: cuentas en la primera, malloc exacto, rewind y llenas en la segunda. Simple, memoria justa, dos lecturas.
  • Crecimiento dinámico: realloc duplicando capacidad en una sola pasada. Una lectura, más código y cuidado con punteros invalidados.

Se eligió dos pasadas por simplicidad de depuración: el conteo es verificable (8v y 6 caras × (4−2)×3 = 36i) antes de tocar memoria. El coste de releer un cubo es despreciable; para modelos gigantes se podría cambiar a realloc sin tocar el API.

5. De base 1 a base 0

OBJ es base 1: el primer v del archivo es el vértice 1. Tu array es base 0: vertices[0] es el primer vértice.

f 1 2 3  →  indices 0 1 2  (siempre idx-1)

Olvidar el -1 no da error de compilación: da geometría rota. Y la bomba: f 8 sobre 8 vértices sin restar lee vertices[8] → fuera de rango, basura o segfault. En la pasada 2 se valida:

if (a<1 || b<1 || c<1 || (size_t)a>v_count || ...) error;
out->indices[i++] = (unsigned)(a-1);

6. Fan triangulation

El GPU dibuja GL_TRIANGLES: cada 3 índices es un triángulo. Una cara con 4 vértices no se puede enviar directa. Abanico fijando el primer vértice:

f 1 2 3 4   →  (1,2,3) (1,3,4)
f 1 2 3 4 5 →  (1,2,3) (1,3,4) (1,4,5)
N vértices  →  N-2 triángulos → (N-2)*3 índices
4 ----- 3
|     / |
|   /   |
| /     |
1 ----- 2

Funciona para convexos simples; falla con cóncavas/no coplanares — justo el bonus de .obj complejos.

7. De la CPU al GPU: VBO, EBO y VAO

Hasta ahora float vertices[] vivía en RAM del programa. El GPU no lo lee solo; hay que subirlo:

GLuint vao, vbo, ebo;
glGenVertexArrays(1, &vao);
glBindVertexArray(vao);

glGenBuffers(1, &vbo);
glBindBuffer(GL_ARRAY_BUFFER, vbo);
glBufferData(GL_ARRAY_BUFFER, mesh.v_count*3*sizeof(float), mesh.vertices, GL_STATIC_DRAW);

glGenBuffers(1, &ebo);
glBindBuffer(GL_ELEMENT_ARRAY_BUFFER, ebo);
glBufferData(GL_ELEMENT_ARRAY_BUFFER, mesh.i_count*sizeof(unsigned), mesh.indices, GL_STATIC_DRAW);

glVertexAttribPointer(0, 3, GL_FLOAT, GL_FALSE, 3*sizeof(float), (void*)0);
glEnableVertexAttribArray(0);
glEnable(GL_DEPTH_TEST);
  • VBO: guarda datos crudos. "¿Dónde están los datos?"
  • EBO: guarda índices. "¿En qué orden se usan?"
  • VAO: recuerda cómo se leen (location 0, tamaño 3, stride, offset) y qué EBO está bindeado. No hagas glBindBuffer(GL_ELEMENT_ARRAY_BUFFER,0) mientras el VAO esté bindeado o lo desenganchas.

glDrawElements(GL_TRIANGLES, 36, GL_UNSIGNED_INT, 0) dibuja 12 triángulos reutilizando 8 vértices. Con glDrawArrays habrías duplicado vértices (36×3 floats) en RAM. Sin GL_DEPTH_TEST + glClear(DEPTH_BUFFER_BIT) el cubo se ve mal: caras traseras pisando delanteras. El triángulo hardcodeado de la clase 2 muere aquí; la infraestructura (ventana, contexto, loader, shaders, swap, poll, terminate) sobrevive intacta.

9. Predicciones y ejercicios

Conviene intentar cada ejercicio antes de consultar la solución.

Ejercicio 1 · contar vértices

Si tu vertices contiene 9 floats y cada vértice tiene 3 floats, ¿cuántos vértices hay?

Mostrar solución

Hay 3 vértices, porque 9 / 3 = 3.

Ejercicio 2 · quad a triángulos

Un .obj dice f 1 2 3 4 y tu array es base 0. ¿Qué índices reales lees y cuántos triángulos generas?

Mostrar solución

Lees 0 1 2 y 0 2 3 (siempre idx-1). Un quad → 2 triángulos → 6 índices. Regla: N vértices → N−2 triángulos.

Ejercicio 3 · v vs vt

¿Por qué sscanf(line, "v %f %f %f") no basta para distinguir v de vt y qué harías?

Mostrar solución

sscanf sobre vt ... falla pero de forma implícita; lo robusto es filtrar por prefijo: s[0]=='v' && s[1]==' ' para vértices, s[1]=='t'/'n' para ignorar.

Ejercicio 4 · formato de Blender

f 1/5/2 2/6/3 3/7/4 viene de Blender (v/vt/vn). ¿Qué parte te interesa y cómo la extraes sin morir?

Mostrar solución

Solo el primer entero de cada token (índice de posición). Con strtol(p,&end,10) lees 1 y paras en /; luego saltas hasta el siguiente espacio.

Ejercicio 5 · dos pasadas

¿Por qué dos pasadas es más simple de depurar que realloc y cuándo cambiarías?

Mostrar solución

Cuentas primero (8v, 36i) y reservas exacto; cualquier descuadre se ve antes de malloc. Con realloc una sola pasada pero más ramas y riesgo de invalidar punteros. Para modelos enormes o streaming cambiaría a realloc.

Ejercicio 6 · loader antes del contexto

¿Qué le pasa al loader si lo llamas antes de glfwMakeContextCurrent y cómo lo evitas?

Mostrar solución

glfwGetProcAddress devuelve NULL (el driver aún no está cargado) y la macro GL_LOAD aborta. Orden fijo: glfwCreateWindow → glfwMakeContextCurrent → init_gl_functions().

Ejercicio 7 · EBO y VAO

¿Por qué el EBO debe crearse con el VAO bindeado y qué rompe si lo desbindeas mal?

Mostrar solución

El binding de GL_ELEMENT_ARRAY_BUFFER se guarda dentro del VAO. Si haces glBindBuffer(EBO,0) con el VAO bindeado, el VAO olvida su EBO y glDrawElements no tiene índices.

Has aprendido que

  • Un .obj es texto: v son posiciones, f son caras con índices base 1, el resto se ignora en clase 3.
  • fgets + skip_ws da una línea limpia por iteración; open/read te habría dado trozos crudos.
  • sscanf valida v con su retorno ==3; para f necesitas strtol token a token para soportar 1, 1/2, 1//3, 1/2/3.

  • El EBO comparte el VAO y se dibuja con glDrawElements; glDrawArrays habría duplicado vértices.
  • GL_DEPTH_TEST es obligatorio para un cubo sólido; sin él el orden de dibujo decide qué se ve.
  • El parser vive antes de glfwInit() y su criterio observable es OBJ OK + 8/36 + cubo visible con -Wall -Wextra -Werror limpio.

1. What we are isolating

This class does not touch MVP matrices or textures. It isolates one question:

How does a line like "f 1 2 3 4" go from disk to triangles the GPU understands?

The minimum flow is:

assets/cube.obj (text)
  ↓ fgets line by line
pass 1: count v and faces → allocate exact
  ↓ malloc + rewind
pass 2: fill vertices[] and indices[] (0-based, fan)
  ↓
t_mesh { vertices, v_count, indices, i_count }
  ↓ glBufferData(GL_ARRAY_BUFFER) + glBufferData(GL_ELEMENT_ARRAY_BUFFER)
VAO (location 0 = 3 floats, stride 3*sizeof(float), offset 0)
  ↓
glDrawElements(GL_TRIANGLES, 36, GL_UNSIGNED_INT, 0)

The parser is intentionally dumb: it only turns text into geometry. Centering, projection and texturing come later.

3. fgets, sscanf and the v trap

For line-by-line text fopen + fgets avoids reimplementing buffering:

FILE *fp = fopen(path, "r");
char line[1024];
while (fgets(line, sizeof(line), fp)) {
    const char *s = skip_ws(line);
    if (*s == '\0' || *s == '\n' || *s == '#') continue;
    // ...
}

open/read gives raw chunks with no guarantee a chunk ends at \n; fgets gives one full line per call.

For v plain sscanf is enough because the format is fixed:

float x, y, z;
if (sscanf(s, "v %f %f %f", &x, &y, &z) != 3) error;

The return value of sscanf is your free validation: asking for 3 and getting 2 means the line is broken. And the robust filter is prefix-based:

if (s[0]=='v' && s[1]==' ') { /* pure v */ }
else if (s[0]=='v' && s[1]=='t') continue;
else if (s[0]=='v' && s[1]=='n') continue;

For f a fixed sscanf with 8 %d never works — a quad has 4 indices (==4 is never ==8) and Blender emits 1/2/3. You must tokenize:

int tmp[64]; int n=0; const char *p = s+2; // past "f "
while (*p && *p!='#' && n<64) {
    char *end; long v = strtol(p, &end, 10);
    if (end==p) break;
    tmp[n++] = (int)v;
    p = end;
    while (*p && *p!=' ' && *p!='\t' && *p!='\n') p++; // skip "/2/3"
    p = skip_ws(p);
}

strtol stops at /, so 1/2/3 yields 1 and the loop skips the rest.

4. Two passes vs realloc

You do not know how many v the file has before reading it. Two strategies:

  • Two passes: count in the first, malloc exact, rewind and fill in the second. Simple, tight memory, two reads.
  • Dynamic growth: realloc doubling capacity in a single pass. One read, more branches and dangling-pointer risks.

Two passes was chosen for debuggability: the counts are verifiable (8v and 6×(4−2)×3 = 36i) before touching memory. Re-reading a cube is negligible; for huge streamed models you could switch to realloc without changing the API.

5. From 1-based to 0-based

OBJ is 1-based: the first v in the file is vertex 1. Your arrays are 0-based: vertices[0] is the first vertex.

f 1 2 3  →  indices 0 1 2  (always idx-1)

Forgetting -1 gives no compiler error: it gives broken geometry. And f 8 on 8 vertices without subtracting reads vertices[8] → out of bounds.

if (a<1 || b<1 || c<1 || (size_t)a>v_count || ...) error;
out->indices[i++] = (unsigned)(a-1);

6. Fan triangulation

The GPU draws GL_TRIANGLES: every 3 indices is a triangle. A 4-vertex face cannot be sent as-is. Fan with the first vertex fixed:

f 1 2 3 4   →  (1,2,3) (1,3,4)
f 1 2 3 4 5 →  (1,2,3) (1,3,4) (1,4,5)
N vertices  →  N-2 triangles → (N-2)*3 indices
4 ----- 3
|     / |
|   /   |
| /     |
1 ----- 2

Works for simple convex polygons; fails with concave/non-coplanar — the bonus for complex .obj files.

7. From CPU to GPU: VBO, EBO and VAO

Until now float vertices[] lived in program RAM. The GPU does not read it on its own; you upload it:

GLuint vao, vbo, ebo;
glGenVertexArrays(1, &vao);
glBindVertexArray(vao);

glGenBuffers(1, &vbo);
glBindBuffer(GL_ARRAY_BUFFER, vbo);
glBufferData(GL_ARRAY_BUFFER, mesh.v_count*3*sizeof(float), mesh.vertices, GL_STATIC_DRAW);

glGenBuffers(1, &ebo);
glBindBuffer(GL_ELEMENT_ARRAY_BUFFER, ebo);
glBufferData(GL_ELEMENT_ARRAY_BUFFER, mesh.i_count*sizeof(unsigned), mesh.indices, GL_STATIC_DRAW);

glVertexAttribPointer(0, 3, GL_FLOAT, GL_FALSE, 3*sizeof(float), (void*)0);
glEnableVertexAttribArray(0);
glEnable(GL_DEPTH_TEST);
  • VBO: holds raw data. "Where is the data?"
  • EBO: holds indices. "In which order are they used?"
  • VAO: remembers how to read them (location 0, size 3, stride, offset) and which EBO is bound. Do not glBindBuffer(GL_ELEMENT_ARRAY_BUFFER,0) while the VAO is bound.

glDrawElements(GL_TRIANGLES, 36, GL_UNSIGNED_INT, 0) draws 12 triangles reusing 8 vertices. With glDrawArrays you would have duplicated vertices (36×3 floats). Without GL_DEPTH_TEST + glClear(DEPTH_BUFFER_BIT) back faces punch through front faces. The hardcoded triangle of class 2 dies here; the infrastructure (window, context, loader, shaders, swap, poll, terminate) survives intact.

9. Predictions and exercises

Try each exercise before unfolding the solution.

Exercise 1 · count vertices

If your vertices holds 9 floats and each vertex has 3 floats, how many vertices are there?

Show answer

3 vertices, because 9 / 3 = 3.

Exercise 2 · quad to triangles

A .obj says f 1 2 3 4 and your array is 0-based. Which real indices do you read and how many triangles?

Show answer

You read 0 1 2 and 0 2 3 (always idx-1). One quad → 2 triangles → 6 indices. Rule: N vertices → N−2 triangles.

Exercise 3 · v vs vt

Why is sscanf(line, "v %f %f %f") not enough to tell v from vt and what would you do?

Show answer

sscanf on vt ... fails but only implicitly; the robust way is to filter by prefix: s[0]=='v' && s[1]==' ' for positions, s[1]=='t'/'n' to skip.

Exercise 4 · Blender format

f 1/5/2 2/6/3 3/7/4 comes from Blender (v/vt/vn). Which part do you care about and how do you extract it safely?

Show answer

Only the first integer of each token (the position index). With strtol(p,&end,10) you read 1 and stop at /; then skip to the next space.

Exercise 5 · two passes

Why are two passes simpler to debug than realloc and when would you switch?

Show answer

You count first (8v, 36i) and allocate exact; any mismatch shows before malloc. With realloc one pass but more branches and pointer-invalidation risk. For huge or streamed models you would switch to doubling realloc.

Exercise 6 · loader before context

What happens if you call the loader before glfwMakeContextCurrent and how do you avoid it?

Show answer

glfwGetProcAddress returns NULL (driver not loaded yet) and the GL_LOAD guard aborts. Fixed order: glfwCreateWindow → glfwMakeContextCurrent → init_gl_functions().

Exercise 7 · EBO and VAO

Why must the EBO be created with the VAO bound and what breaks if you unbind it wrong?

Show answer

The GL_ELEMENT_ARRAY_BUFFER binding is stored inside the VAO. If you glBindBuffer(EBO,0) while the VAO is bound, the VAO forgets its EBO and glDrawElements has no indices.

Common mistakes
  • Writing a single face f 1 2 3 4 5 6 7 8 and believing it is a cube.
  • Using sscanf(line, "f %d %d %d %d %d %d %d %d")==8 so quads (4 indices) never match.
  • Forgetting idx-1 and reading vertices[1] for f 1, or worse vertices[8] for f 8 → out of bounds.
  • Filtering v with sscanf without telling vt/vn apart.
  • Parsing 1/2/3 as a big integer instead of taking only the 1.
  • Doing realloc for no reason and fighting invalidated pointers.
  • Creating the EBO without a bound VAO or unbinding it at the wrong time and losing the indices.
  • Forgetting GL_DEPTH_TEST and GL_DEPTH_BUFFER_BIT and seeing back faces in front.
  • Putting the parser after glfwInit and not being able to validate the .obj without a display.
  • Leaving the hardcoded triangle next to the cube and drawing 3 vertices instead of 36 indices.

You have learned that

  • A .obj is text: v are positions, f are 1-based faces, the rest is ignored in class 3.
  • fgets + skip_ws gives one clean line per iteration; open/read would have given raw chunks.
  • sscanf validates v with its return ==3; for f you need token-by-token strtol to handle 1, 1/2, 1//3, 1/2/3.
  • OBJ 1-based → 0-based is always idx-1; validating 1..v_count avoids silent segfaults.
  • Fan triangulation: f a b c d → (a,b,c) (a,c,d); N vertices → N−2 triangles.
  • Two passes allow exact malloc and count-based debugging (8v/36i); realloc is for streaming.
  • The EBO shares the VAO and is drawn with glDrawElements; glDrawArrays would have duplicated vertices.
  • GL_DEPTH_TEST is mandatory for a solid cube; without it draw order decides visibility.
  • The parser lives before glfwInit() and its observable criterion is OBJ OK + 8/36 + visible cube with a clean -Wall -Wextra -Werror build.
